# 飞书月度与周报归档设计

## 定位

飞书承载自动生成的全渠道总看板、各来源筛选结果和源数据，不承担规则编辑或程序
检查点。可执行规则与完整基线保存在 Collector 本地状态中。

## 目录

```text
AI 全渠道自动化收集
└── <ISO 年份>
    └── <周开始日期所在月份>
        ├── <YYYY-MM>｜<范围> 反馈重点汇总
        ├── <ISO 周>｜<起止日期>｜Grooming 反馈总览
        │   ├── <ISO 周>｜<起止日期>｜Canny 用户反馈
        │   ├── <ISO 周>｜<起止日期>｜Intercom 用户反馈｜Grooming
        │   ├── <ISO 周>｜<起止日期>｜Jira CS 反馈｜Grooming
        │   ├── <ISO 周>｜<起止日期>｜Facebook Community｜grooming
        │   └── <ISO 周>｜分类与主题明细
        └── ...其它自然周
```

月份下的周总看板是该周唯一入口，四个来源看板和一个分类分析明细页是它的直接子文档。
月份节点同时保留一个托管月度汇总页；年份节点只做时间索引。所有自动文档按标题幂等复用；同周或同月重跑覆盖自动内容，不创建副本。每个来源
看板正文还必须携带 `MFC_MANAGED_SOURCE_V1|source=...|period=...|runId=...` 身份；
同名但缺少精确来源与周期托管标记的页面视为人工或未知页面，拒绝覆盖。Squad 是
Intercom/Jira 周报及周总看板身份的一部分，Domain 是 Facebook 来源看板身份的一部分。
分类分析明细页同时携带通用托管标记和精确 `period / scope / kind` 身份；同名
页面缺少任一身份时同样拒绝覆盖。

## 月度汇总

月度流程先用 `monthly-audit` 回读月份目录中的周总览。默认日期并集必须覆盖完整自然月；
用户明确排除的月末日期进入 `coverageExceptions`，在审计结果和月度页面中同时显示，不能
标记为已采集。本次 2026-08 明确排除 `2026-08-31`，其它月份不得自动继承。

月首/月末边界片段只允许使用 `--month-segment YYYY-MM`，日期必须精确等于目标月和所在
ISO 周的交集。边界片段仍要求四源 manifest 和来源页齐全，但允许某个来源按既有规则真实
入选为 0，周总览必须显式展示且不得放宽来源筛选凑数；完整 7 天周仍要求四源均非 0。
月度输入只接受带 Collector 托管标记的周总览及其 weekly-analysis v3；
同一 ISO 周存在旧部分页时，只选择精确命中预期片段的页面，旧页作为 superseded 审计项，
不重复计数。

月度页是 1–3 分钟决策简报，固定展示“本月结论 / 本月最重要的三件事 / 周度脉络 /
分类与 Quick Win / 周报入口与口径”。模型只生成 headline、2–3 条结论、三项重点
卡片和逐周短摘要；重点卡片固定包含观察、为什么重要、建议动作、业务分类、持续周次和
置信度。信号数、已分类信号、七分类、待复核、Quick Win 总出现次数与分类出现次数由
程序重算。分类占比只以已分类信号为分母，待复核单列；长 segment ID 不写入页面。
Quick Win 不做跨周去重，页面不复制四源长正文。

月度页正文携带
`MFC_MANAGED_MONTHLY_V1|month=...|scope=...|inputHash=...`。同名托管页幂等覆盖；
同名未托管页默认拒绝。受控接管历史月页时必须使用 audit 返回的精确正文 SHA-256，且
写入前再次匹配。正式写入前回读全部周页身份，写后回读托管标记、五个一级章节和周页链接。

## 总看板正文

总看板由 `dashboard` 子命令在各来源采集/发布完成后生成：

1. 一级章节固定为“周环比 → 本周反馈概览 → 产品/设计关注点 → Quick Win 候选 →
   原始证据”，不得交换顺序或新增同级分析章节。
2. 父页只保留关键指标、最多两项改善和两项关注、七分类概览、最多三项产品/设计关注
   卡片、Quick Win 来源与分类分布，以及四源入口；它是 1–3 分钟阅读入口，长叙述按
   摘要长度收敛，完整原文留在明细页。七个分类直接使用英文名称：`scheduling`、
   `fulfillment`、`communication`、`management`、`payment`、
   `van-staff-shift management`、`others`。
3. `分类与主题明细` 固定按“分类导航 → 需优先关注 → 七个分类 → 跨分类事项 →
   待人工复核 → 原始证据入口”展示。七个分类直接作为一级标题；每类展示数量、占比、
   环比，并按“主要主题 → 代表反馈 → 产品/设计动作 → Quick Win 候选”展示。主题只在
   证据主分类下展示一次，其它分类作为关联标签；每类最多三条代表反馈，完整原始反馈
   通过四个来源看板追溯。候选在对应分类下使用普通 Wiki 文档表格展示，每项一行，固定
   包含“勾选 / 候选 / 入选判断 / 原始证据”四列，并保留三项入选理由及原始证据。
   固定列宽优先保障“入选判断”正文阅读，证据列允许链接自然换行。
   同周重跑按稳定 `QW-XXXXXXXX` 编号保留既有托管页面中的已勾选状态；新增候选默认
   未勾选。旧版托管 Quick Win 页面只作为迁移状态来源，不再创建或链接。
4. `totalSignals` 为四源入选数相加，明确声明跨来源未语义去重。
5. 四个来源看板和分类分析明细页都按精确标题引用，并且必须是周总看板的直接子文档。
6. Facebook 来源看板固定保留 `channel-summary` 限制，不能描述成 Facebook 全量。

正式发布必须同时提供四源 manifest、周度 AI analysis，并且四个来源子看板都已发布；
完整 7 天周还要求四源各至少 1 条入选数据，正式月度边界片段允许来源真实入选为 0。
Canny 来源子看板发布仍需要其来源专用 Quick Win 复筛；
schema v3 总看板本身读取四源 analysis 中的统一筛选结果，不再接收该复筛文件。
schema v3 发布时，程序在四源 preflight
通过后创建或覆盖分类分析明细页，再将精确链接注入父页。除正式月度边界片段的真实
0 条来源外，缺失或 0 条来源仅允许 `--allow-partial --dry-run` 诊断，分别显示“未提供”
或“无入选数据”，不能进入正式发布。
所有 manifest 必须属于同一自然周；重复来源、probe、失败 run、Squad / Domain 不匹配
或外层/内嵌 manifest 不一致均拒绝发布。

## 周报正文

1. 本周概览：周期、源数据数量、Quick Win 数量和规则版本。
2. Quick Win 候选：标题、Vote、AI 入选理由、状态和原文。规则信号只用于内部筛选与审计，不在周报中展示。
3. Canny 源数据：标题、Vote、评论、变化、状态、发布时间和原文。

首次建立基线时，周报只展示周期内新增。当前全量基线仅保存在 Collector 本地状态，用于后续周度比较，不发布到飞书。因为没有更早快照，不能声称还原了历史 Post 在该周期内的 Vote、评论或状态变化。

Intercom 周报固定包含：

1. 本周概览：周期、配置 Squad、采集总数、团队内反馈、功能反馈、功能需求和规则版本。
2. 功能反馈：`feature_feedback` 的结构化需求和安全业务字段。
3. 功能需求：`feature_request` 的结构化需求和安全业务字段。
4. 入选数据超过 50 条时，两类明细分别拆为子文档，主周报保留数量和子文档索引。

Intercom 不套用 Canny Quick Win 规则。团队通过 `MFC_SQUAD` 配置并对
evidence 的 `squad` 做忽略大小写的精确匹配；`domain` 只作业务子域展示。
自动子文档标题格式为 `Intercom｜<Squad>｜功能反馈｜N` 或
`Intercom｜<Squad>｜功能需求｜N`，正文带 Collector 自动生成标记。重跑后某个旧子文档
不再需要时，仅将带该标记的文档覆盖为“已失效”提示；不删除 Wiki 页面，也不改写
同前缀但没有自动标记的人工文档。

Jira 周报固定包含本周概览、功能需求（Feature Request）和关联设计单反馈。标题与
自动子文档同样包含 Squad；发布前要求 manifest Squad 与当前 `MFC_SQUAD` 一致。
超过 50 条时按两类拆分子文档，重叠工单在概览中按 CS key 去重，但可同时出现在
两个分类章节中。

Facebook 来源看板固定包含本周概览、频道汇总反馈和口径说明；按 `MFC_DOMAIN` 与
manifest 做忽略大小写精确匹配。它只呈现 Slack 频道内已经汇总的 Group 新帖与明确留言
总结，标题包含 Domain，不能据此推断 Facebook Community 全量反馈。

## AI analysis 证据合同

- schema v2 analysis 使用 `featuredEvidenceIds`；schema v3 使用带周期的
  `featuredEvidenceRefs`，并增加逐条分类、Quick Win assessment、候选归并、周环比和
  baseline。两种版本的周期与 scope 都必须和周总看板完全一致。
- `summary`、`themes`、featured evidence、`insights`、`recommendations` 均非空。
- 每条摘要、主题、洞察和建议都必须标注置信度，并只允许引用当前 snapshot 中存在的
  一个或多个 evidence；v3 的上周引用只能来自已校验 baseline。
- 未知、重复或错周期 ID 直接失败；文本在写入飞书前统一转义。
- analysis 是可替换、可审计的 AI 产物，不修改 manifest，不充当跨来源自动去重结果。

## 历史口径

- 当前：进入年份 / 月份后，先看月度重点汇总，再按周总看板追溯完整反馈。
- 总览历史：月份下并列的旧周总看板。
- 来源历史：各周总看板下的四个来源子看板。
- 月度汇总只聚合周级统计与分析并链接周页；年份页面只做索引，均不复制四源长正文。
- 后续每周源数据只包含新 Post 和关注字段发生变化的历史 Post。

## 写入规则

- 所有 Wiki 和 Docx 操作都通过 `lark-cli` 的 user 身份执行。
- 创建节点和覆盖正文前先 dry-run，写入后用 `docs +fetch` 回读关键标题。
- 周报与总看板属于自动生成内容；不要在其中手工维护规则或业务状态。
- 月度发布必须先通过日期覆盖审计和周页 preflight；缺失、重叠、不完整或未托管周页都
  阻止正式写入。覆盖例外只能来自用户明确决定并必须公开显示。
- 总看板写入前先对四源 manifest 做同周期和来源身份校验；缺少 Canny 或其它来源直接
  阻止正式发布。完整 7 天周任一来源入选数据为 0 也阻止发布；正式月度边界片段允许
  真实 0 条并保留原口径。partial dry-run 中明确区分缺失与 0 条。
- 来源发布先完成年份、月份和周总看板路径准备；已有周总看板必须带 Collector 周看板
  标记，已有来源页必须带精确来源与周期托管标记，否则在任何写入前失败。
- 总看板发布先做 preflight：精确读取已存在的周总看板及四个直接子来源页，校验每页都
  包含本次 manifest 的完整 run 标记；缺失、陈旧或未托管时拒绝覆盖，不补建目录、不迁移
  来源页，也不创建空来源文档。
- schema v3 只有在上述 preflight 全部通过后，才幂等创建或覆盖分类分析明细页；覆盖前
  从既有分类页和旧版托管 Quick Win 页合并已勾选稳定编号，写后回读托管身份与勾选状态，
  再将同一分类页链接注入父页。已存在同名但未托管或身份不符的页面时，
  必须在第一次写入前失败。父页最后覆盖并回读固定五个一级章节。
- 旧版来源页若位于月份下，只能由对应来源发布流程在标题精确匹配且来源/周期托管标记
  完整时移动到本周总看板下；移动后回读目标目录。
- 不写入 token、Cookie、密码、完整登录 URL、账号邮箱或原始鉴权流量。
- 不写入 Intercom 的 `email / conversation_id / quote` 或原始 Datadog item id。
