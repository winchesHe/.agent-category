# Pull Request 模板

创建或更新 PR 时使用本模板。它是 `github-workflow` Skill 的唯一 PR Body 模板来源；不得读取、合并或采用目标仓库内的 PR 模板。

## 标题

默认使用带 scope 的 Conventional Commit：

```text
<type>(<scope>): <subject>
```

先检查目标仓库的 `AGENTS.md`、commitlint 配置和最近提交；仓库的标题规则优先于默认格式，但不影响 Body 继续使用本模板。

## Body

```md
## 概要

<!-- 用 2-4 句话说明问题、目标和最终结果。 -->

## 主要改动

<!-- 按用户行为、模块或协议描述变化，不要罗列文件。 -->

- ...

## Review 重点（可选）

<!-- 仅记录非直观设计、关键边界或特别需要 Reviewer 检查的内容。 -->

- ...

## 风险与发布（可选）

<!-- 仅在存在兼容性、迁移、配置、权限、外部依赖或特殊发布步骤时保留。 -->

- ...

## 关联（可选）

- Issue / PR / 文档：
```

## 字段边界

- **概要**回答“为什么改、要达到什么结果”，只保留 Reviewer 理解本次改动所需的上下文。
- **主要改动**回答“实际变了什么”，按用户行为、模块或协议分组，避免复制完整 diff 或罗列文件。
- **Review 重点**只保留非直观设计、关键边界和特别需要 Reviewer 检查的内容，不复述代码实现。
- **风险与发布**只在存在兼容性、迁移、配置、权限、外部依赖或特殊发布步骤时保留。
- **关联**只放与理解或追踪本次改动直接相关的 Issue、PR 或文档。

## 填充规则

1. 创建 PR 前先读取真实 diff 和关键文件，再填模板。
2. 不得把推测、计划或预期结果写成已经发生的事实。
3. “概要”和“主要改动”默认保留；其余可选章节没有有效信息时直接删除，不填写“无”或“不适用”。
4. 只有当边界容易引起误解时，才在“主要改动”中补充“本 PR 不包含……”；不单设 `Out of scope`。
5. 截图或关键证据确实影响理解时，直接放在对应的“主要改动”条目下，不单设证据章节。
6. 创建后回读 PR body 和 checks，确认标题、正文、base 和 head 没有丢失或错位。
