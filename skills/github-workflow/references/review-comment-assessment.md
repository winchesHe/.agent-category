# Review Comment Assessment

本文件只在处理 GitHub review comment / review thread 时加载。目标不是把评论逐字翻译成代码，而是确认评论指出的事实、业务问题和修复处方分别是否成立。需要代码证据时，由主 agent 直接核对代码、调用链、契约、测试和业务不变量；处理单条 review comment 不自动调用 `review-swarm`。只有用户另行明确要求完整代码 review / PR review 时，才按 `github-workflow` 的代码审查路由调用 `review-swarm`。

## 核心原则：事实、问题、方案分开判定

一条评论通常包含三种不同主张：

1. **事实主张**：当前代码在某些条件下会发生什么。
2. **问题主张**：这个行为是否违反了产品意图、业务契约或代码库约束。
3. **方案主张**：评论建议的改法是否能安全修复问题，并保留其他合法行为。

不得因为事实主张成立，就自动接受问题主张或方案主张。先从局部代码扩展到系统影响，再回到业务契约核对。

| 事实 | 业务问题 | 建议方案 | 处理 |
|---|---|---|---|
| 不成立 | — | — | 说明可复现证据，不修改 |
| 成立 | 不成立，行为符合预期 | — | 说明意图和证据，不修改 |
| 成立 | 成立 | 安全可行 | 修改、验证、提交和推送 |
| 成立 | 成立 | 会破坏其他合法流程 | 保留问题结论，设计替代修复，不照搬建议 |
| 无法确认 | 无法确认 | 无法确认 | 补充证据或澄清，先不改 |
| 成立 | 成立 | 可行但超出当前范围 | 记录后续任务，不扩大本次 PR |

## 处理前的上下文包

在实质修改前记录以下信息；临时快照放在 worktree 外：

- `owner/repo`、PR 编号、base/head branch 和初始 `headRefOid`。
- 原始 comment ID、review thread ID、文件、行号、作者和当前 `isResolved` / `isOutdated` 状态。
- PR 描述、关联 issue、设计或验收文档，以及适用的 `AGENTS.md` / `CONTEXT.md`。
- 当前行为、预期行为、非目标和可观察验收条件。
- 明确来源的约束与根据代码推断的假设；两者不要混写。

评论目标不清、评论已被删除、thread 无法唯一定位或 PR head 已变化时，先停止，不猜目标。

本规则的自动回复默认针对可由 `thread_id` 唯一定位的 inline review thread。普通 PR conversation comment 或 review body 没有原生线程回复关系时，不猜测关联对象，也不自动新发一条顶层评论；需要时由用户明确指定回复方式。

## 审查边界

评论处理不是完整代码 review。即使评论涉及代码行为、调用链或差异，也直接沿用本文件的三层判定和通用维度，由主 agent 收集足够证据后作决定，不要求启动 `review-swarm`。这样可以把审查成本和上下文范围控制在评论真正要解决的事实、业务问题与修复处方上。

若用户把任务扩大为“完整代码 review”“审查整个 PR / branch / commit / diff”，则切换到 `github-workflow` 的代码审查路由，显式调用 `review-swarm`；该调用产生的 finding 不能替代本文件对某条评论的三层判定。

## 通用审查维度

按风险选择深度；低风险 Nit 不必执行完整业务审计，高风险行为变化必须覆盖所有适用维度。

### 1. 评论语义与意图

- 评论是在报告 bug、提问、要求不同设计、给出可选 suggestion，还是表达风格偏好？
- 评论真正想保护的用户结果或约束是什么？
- 它是阻塞性要求还是非阻塞建议？

把评论改写为可验证句子：**在条件 A 下，当前行为 B 导致结果 C；评论希望保持或改变结果 D。**

### 2. 新鲜度与范围

- 评论针对的 commit 是否仍是当前 PR head？
- 代码行是否已移动、修改或变成 outdated？
- 该意见是否属于当前 PR，而不是其他文件、分支、评论或后续任务？

`isOutdated` 只能说明行位置发生变化，不能单独证明评论无效；仍需验证原意是否被当前代码解决或改变。

### 3. 事实与证据

- 能否通过最小输入、调用路径或测试复现？
- 观察到的是实际行为、预期行为，还是推断？
- 是否检查了调用方、被调用方、测试、历史实现、日志或指标？
- 量词是否与证据相称；不要用一个反例推导“所有”场景。

没有可复现条件或具体 symbol 时，将结论标记为“事实不足”，不要凭直觉修改。

### 4. 业务契约与不变量

逐条写出：主体、动作、目标、租户/作用域、允许项、禁止项、例外和业务原因。特别核对：

- 用户角色、权限和多租户隔离。
- 状态机及允许的状态迁移。
- 金额、计费、库存、配额和数据归属。
- 必须保持的正向流程与明确禁止的流程。
- 看似反直觉但有意为之的行为。

如果评论只描述局部技术现象，却没有证明违反了业务契约，不要把它升级成缺陷。

### 5. 根因与修改处方

分别评估“问题是什么”和“应该怎么改”：

- 建议是否解决根因，还是只遮住症状？
- 直接应用 suggestion 会不会删除合法分支、改变顺序或扩大权限？
- 是否存在更小、更安全、与现有领域规则一致的替代方案？
- 不修改、照改、采用替代方案三种结果分别会保护或破坏什么？

允许输出“问题成立但建议不适用”；这不是拒绝评论，而是保留诊断并拒绝不安全的处方。

### 6. 系统影响与副作用

检查完整调用链和数据流，而不只看被标记行：

- 上下游调用、状态迁移和事务边界。
- API、事件、消息、SDK、数据库和缓存契约。
- 通知、审计、计费、异步任务等外部副作用。
- 错误分类、fallback、资源清理和可观测性。

### 7. 边界、对抗与可靠性

按场景检查：

- 空值、空集合、极限值、重复数据。
- 重试、超时、部分失败、未知结果和补偿。
- 并发、竞态、乱序、重复消费和幂等性。
- 越权、伪造请求、跨租户访问和不诚实用户。
- 日期、时区、本地化和状态回退/跳步。

金额、权限、删除、状态和外部副作用相关评论，默认按高风险处理。

### 8. 兼容、迁移与发布

评估行为变化对以下对象的影响：

- 旧客户端、公开 API 和已有调用方。
- 数据库、事件、缓存或持久化格式。
- feature flag、灰度、回滚、迁移和 backfill。
- 版本协商、部署顺序和失败后的恢复路径。

### 9. 非功能与运维

只有能结合真实路径、频率或规模说明影响时，才提出性能或资源问题。必要时检查：

- 热路径上的额外 I/O、N+1、无界增长和成本。
- 日志、指标、告警、审计和客服排障能力。
- 发布后如何发现问题，以及是否有安全回滚路径。

### 10. 验证与回归证据

验证业务规则和不变量，不只验证实现细节。按风险补充：

- 评论描述的失败路径和原本合法的正向路径。
- 边界、负向、顺序、重试、幂等、并发和权限场景。
- 兼容旧数据/旧客户端的集成或端到端验证。
- 必要的静态、安全、模糊、性能或可观测性检查。

## 风险分级

| 风险 | 最低审查深度 |
|---|---|
| 低：命名、格式、可选可读性 | 局部上下文；确认不是行为要求 |
| 中：普通行为或错误路径 | 契约、调用链、边界和针对性回归测试 |
| 高：金额、权限、删除、状态、并发、外部副作用 | 完整不变量、对抗/并发、兼容迁移、回滚和可观测性；必要时请领域 reviewer |

## 结果标签与记录

每条评论都要选择一个结果：

- `需要修改`：事实成立、违反契约且已找到安全方案。
- `问题成立但建议不适用`：诊断成立，但原建议会破坏其他合法行为。
- `符合预期`：行为与已确认的业务契约一致。
- `事实不足，需澄清`：证据或意图不足以改变代码。
- `有效但超出当前范围`：问题真实，但应拆为后续任务。
- `建议性，不阻塞`：可选改善，不影响当前交付。

建议保留以下最小记录：

```yaml
comment_id: <原评论 ID>
thread_id: <原 thread ID>
target_head: <开始审查时的 SHA>
comment_type: bug | question | alternative | suggestion | nit
claim: <评论指出的可验证事实>
intended_outcome: <要保护的用户结果或业务不变量>
evidence: <复现、调用链、契约或测试证据>
claim_status: true | false | unclear
contract_status: violated | intentional | unclear
proposal_status: safe | unsafe | unclear | out_of_scope
impact: <跨模块、兼容、可靠性或运维影响>
decision: <上述结果标签>
validation: <测试或其他验证>
next_action: <修改、回复、澄清或后续任务>
```

## 修改、推送和回复的顺序

评论处理的远端写入必须按以下顺序：

1. 锁定初始 PR head 和目标 thread。
2. 加载本文件，直接收集与评论相关的代码、调用链、契约、测试和业务证据，完成事实、业务问题和修改方案三层判定。
3. 形成判定前重新读取并比较 PR head、目标 thread 的 ID、`isResolved`、最新回复和目标行状态；任何变化都停止并重新绑定。
4. 只有 `需要修改` 或采用安全替代方案时才改代码；修改前再次确认 PR head 未被他人推进。
5. 验证后按写协议执行 commit 和普通 push。
6. push 成功并回读远端 branch SHA 后，再回读同一 thread。
7. 若本次改动确实由该评论触发，且用户没有显式禁止回复，则回复原 review thread；不得回复其他评论。
8. 回复正文说明事实判断、采用的方案、验证证据和 commit SHA；不要自动 resolve thread。

push 失败、结果不确定、远端 head 出现并发变化、目标 thread 消失/无法唯一定位或已被他人 resolve 时，不发送回复；如 push 已成功，必须报告“代码已推送、评论回复待处理”，并按 ID 回读后再决定是否继续。

本次自身改动导致 thread 显示 `isOutdated=true` 时，不能仅凭这一字段阻止回复；只要 thread ID 仍存在、没有并发 head 变化且回复目标明确，仍可回复原 thread。

## 回复模板

事实和方案都成立时：

> 已核对评论指出的触发条件，确认当前行为会违反 `<业务约束/用户结果>`。已在 `<commit SHA>` 中完成修复，并通过 `<验证>`。

事实成立但建议不安全时：

> 评论指出的现象成立，但直接按建议修改会破坏 `<其他合法流程/不变量>`。因此没有直接应用该方案，改为 `<替代方案>`，已在 `<commit SHA>` 中通过 `<验证>` 确认两条路径均保留。

符合预期或证据不足时，没有代码改动和 push，不触发本规则的自动回复；如用户明确要求回复，才单独执行回复门禁。
