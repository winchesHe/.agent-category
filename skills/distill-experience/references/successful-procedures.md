# 成功经验与操作手册

需要提取成功路径、还原可复现操作，或形成自己复用、交接培训的手册时读取。来源发现与共同证据规则沿用主文件；这里展开怎样把执行记录转成下一次可操作的流程。

## 确定成功的范围

先从原始目标和验收结果判断实际完成到了哪一步。把“任务最终目标”“这次已经验证的阶段结果”和“尚未验证的环节”分开。

例如，请求到达目标服务，只能证明相应请求的路由结果；业务返回错误时，不能将流程命名为“业务端到端跑通”。手册仍可保存已验证的路由检查步骤，并标明后续业务环节的缺口。

优先寻找直接结果及其回读：生成产物是否含所需内容，配置是否实际生效，请求是否关联到正确环境，业务状态是否完成。若只有完成声明，继续回溯声明引用的输出或文件；无法取得时说明验证边界。

## 从执行记录提取有效路径

先恢复历史中实际成功的路径，再判断其中哪些动作值得保留。不要仅凭操作先后认定必要顺序，也不要为了得到更短流程而删除未经判断的前提。

| 动作类型 | 判断依据 | 手册写法 |
|---|---|---|
| 前置准备 | 后续操作需要已有资源、工具、权限、配置或数据 | 写清需要达到的状态，以及如何确认已满足 |
| 必要步骤 | 后一步依赖该步产物或状态，有协议、实现或实测依据 | 保留步骤、输入输出和顺序原因 |
| 条件分支 | 只有特定环境、版本或状态需要 | 写明可观察触发条件及对应动作 |
| 临时绕过 | 解决当次阻塞，但保留限制或额外状态 | 单列适用条件、代价及后续处理，避免成为默认路径 |
| 偶然操作 | 与目标没有已证实的依赖关系 | 不写成必需；影响尚不清楚时保留疑点 |
| 失败探索 | 未形成最终路径，但能区分常见错误 | 只保留有诊断价值的部分，按排障方法展开 |

必要性没有被证明时，使用“该条件下已验证的路径”，不要改写成“必须这样做”或“只有这一种方式”。多个等价入口分别验证过时，按使用目的选择默认入口，并说明其他入口的适用条件；未验证的替代方案不混进成功路径。

## 补齐下一次执行所需信息

从实际记录、产物和对应版本的实现中核对以下信息，缺失时标注，不自行补造：

- **操作对象**：项目、资源、服务、文件或数据范围，以及定位方式。
- **执行环境**：版本、分支、工作目录、运行入口及必要工具状态。
- **配置与命令**：真实参数名、配置键、相对路径的解析位置、请求入口、替换值来源。
- **输入与输出**：前一步产生的标识、文件或状态，下一步如何使用。
- **观察位置**：应查看的文件、返回结果、日志关联方式或业务状态。
- **成功判据**：每一步完成的信号，以及最终目标的验收证据。

命令中把凭据和每次变化的值参数化，说明如何取得参数；不要将历史 token、账号数据或资源标识当作通用默认值。保留必要的引号、工作目录和环境变量作用范围，避免复制后语义改变。

命令或接口已变化时，将核验后的当前入口写入正文，同时说明本轮只核对实现还是实际调用过。历史成功不能自动为新命令背书。

## 检查跨步骤衔接

沿最终操作顺序做一次输入输出核对，重点寻找历史任务中隐含但手册里遗漏的条件：

1. 上一步的输出是否明确成为下一步输入，标识和文件名是否一致。
2. 某个配置是在当前 shell、当前请求、某个进程还是持久存储中生效；换上下文后是否仍可用。
3. 历史成功是否依赖预先存在的资源、缓存、登录态或后台进程；新环境需要怎样确认这些条件。
4. 等待或重试是否有实际必要，等待什么可观察状态后继续；不要把一次等待时长当作固定经验。
5. 中途失败后能从哪一步继续；重复操作是否会创建额外资源或改变业务状态。
6. 临时配置与产物是否需要恢复或清理，依据是什么；没有相应需求时不编造清理步骤。

只有静态核对时，结论是“步骤和来源已核对”，不能称为“完整复跑通过”。实际复跑应遵守本次允许的操作范围，不为了提炼经验而重放有外部副作用的历史动作。

## 组织手册

正文按下一次要解决的问题组织。面向交接补足背景与入口，面向熟悉系统的本人复用可减少背景；关键参数、顺序与判据保持完整。

同一主题已有权威手册时，使用积累 reference 判断修订或合并。不要再创建一份内容相同但名称不同的“经验总结”。

## 交付前检查

选一条正文中的实际操作路径，从前提读到最后判据：必要的信息是否均在正文或可用引用中，是否仍需向原操作者索取关键步骤？检查标题中的“成功”范围与证据一致；检查每条故障建议是否与来源匹配。

需要验证复用效果时，选择一个没有参与提炼的相似任务，检查使用者是否能找到入口、选对分支、完成操作及识别不适用条件。其价值不以是否创造新知识衡量，而以是否减少必要的重新调查并支持正确执行衡量。
