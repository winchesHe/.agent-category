# 排障、试错与纠正

证据包含失败、重试、假设推翻、用户纠正或根因判断，或已有经验仍反复失效时读取。目标是从已有经历中提取诊断方法与有效动作；需要新的排障执行时，以本次任务范围和允许动作决定是否继续。

## 串起关键尝试

从原始目标与可观察失败开始，按时间恢复影响判断的尝试。只保留有信息增量的步骤，不把完整操作流水直接复制为经验。

每次尝试记录：当时的假设、相关环境与前提、实际改变了什么、看到什么结果、据此排除了什么，以及后续是否被纠正。命令重试但条件没有变化时，可以合并叙述；同一失败被多个会话转述时按共同规则去重。

检查变化的独立性：

- 一次只调整一个因素且有前后对照，通常更容易判断其贡献，仍需检查同时变化的环境。
- 多项改动后恢复，只能先描述该组合下的结果；没有独立证据时，不认定每项改动都是必要原因。
- 撤销改动后仍正常、重新执行又失败、不同环境表现不同，都是限制因果解释的重要证据。
- 未再出现错误、短期日志为空或重试返回成功，只能证明相应观察范围内的结果，不能直接证明根因消失。

## 区分解释的层次

| 层次 | 需要的依据 | 可以写到什么程度 |
|---|---|---|
| 症状 | 返回、日志、产物或业务状态中的直接观察 | 描述条件与现象，不预设原因 |
| 触发因素 | 某条件与失败出现的关联，以及边界记录 | 说明何时容易出现，不等同于根因 |
| 根因 | 能解释观察且得到实现、对照或其他直接证据支持 | 写清机制、证据和仍未排除的解释 |
| 临时绕过 | 在特定条件下恢复局部能力的执行结果 | 写清适用范围和残留问题，不宣称机制已修复 |
| 已验证修复 | 改动后对相应失败路径及目标结果的验证 | 描述实际覆盖，不扩大为所有环境均有效 |
| 待验证假设 | 合理解释，但关键证据不足 | 保留候选与可检验方法，不写成事实 |

没有确认根因，也可以提炼有用的诊断步骤：例如确认故障发生在路由之后，或排除参数未传入的解释。保留这类进展，并明确问题尚未解决。

## 写成诊断分支

每条有用的排障经验应帮助执行者改变某个具体判断或动作。围绕以下关系组织，不强制使用固定字段模板：

**遇到什么症状 → 查什么证据 → 不同结果分别说明什么 → 下一步怎样做 → 怎样确认有效。**

优先选择能够区分候选解释的证据，避免列出一串与判断无关的通用检查。核对当前版本中日志、指标或工具结果的实际语义：某个数字、状态或成功返回究竟证明了哪一步，仍不能证明什么。

处理建议按证据状态表达：

- 已验证修复：保留具体动作、前提和成功判据。
- 可用诊断线索：说明观察与判断的关系，以及应继续取得的证据。
- 待验证动作：明确未执行，说明预期能检验哪种解释；不写成“照此即可修复”。

高代价或曾导致错误的动作若需要限制，应绑定实际触发条件、原因及可行替代；不把单个案例变成“永远不要使用某工具”的全局禁令。

### 示例：路由命中但业务失败

假设一次请求在入口与目标服务中都有对应关联记录，但业务仍返回错误。可提炼为：先按请求标识核对路由与环境，再检查同一请求的业务状态和失败信息。路由证据只支持到达目标服务的结论，业务完成需要自己的验收依据。

若随后短时间内未再出现相同错误，只记录检查过的时间窗口和条件。没有相应元数据或业务结果时，不推导“系统会自动修复”。这条经验能够帮助下次区分调查层次，即使尚未找到最终修复。

## 理解用户纠正

回读纠正前的要求、实际交付和纠正后的目标，判断纠正针对什么：事实错误、任务范围、执行方式、产物可用性，还是明确的长期偏好。不要只提取“不对”“以后”之类关键词。

以可观察变化记录经验。例如，原交付只有概述，纠正要求补齐操作参数与判据，则改进应对应“需要复用手册时如何保留细节”，不能泛化为所有回答都必须更长。

对于多次纠正，先按独立事件关联，再核对它们是否适用同一范围。明确约定可以直接证明相应要求；无法从纠正本身推导其已经通过效果验证。

## 已有经验仍然复发

先查已有承载及实际执行记录，再判断原因；缺少读取轨迹时标注未知，不推断“Agent 故意忽略”。

| 观察 | 优先调查 | 可能的改进方向 |
|---|---|---|
| 没有发现对应经验 | 标题、症状词、索引和检索范围是否匹配 | 改善可发现性，补正确引用 |
| 找到入口但未读到关键内容 | 加载条件是否明确，细节是否藏在未读 reference | 调整加载条件或关键提醒的位置 |
| 已读内容但场景不同 | 环境、前提、触发条件是否不适用或过宽 | 修订适用范围，补分支 |
| 已读且条件匹配，步骤仍不成立 | 内容是否过时、证据是否误判、步骤是否缺项 | 修订知识，重新核验 |
| 判断正确但动作难执行或易遗漏 | 是否有稳定可机械检查的要求和已有验证能力 | 优先复用 validator；必要时提出具体实现建议 |

不要直接新增同义规则、按照次数自动晋升，或将所有复发问题转换成 hook。承载变更仍需满足主文件的行为变化六项及本次授权。

## 验证排障经验与行为改进

先核对原案例中，正文建议是否会改变实际判断或下一步动作。再检查它是否过早排除了其他解释、依赖不存在的证据，或把局部恢复写成完整修复。

需要固化行为时，预先定义观察目标，如能否识别原误判、减少无条件重试、取得真正区分原因的证据。按影响范围检查相似任务与不适用边界；不能以“写出了该条规则”代替验证。

未实际尝试的替代动作、无法复现的条件和仍有冲突的解释，放在具体缺口中。最终交付以可用诊断方法为主，不要求每次给出完整根因或新增长期规则。
