# 按问题选择调查路径

这些路径帮助定位证据，不是每次必须跑完的清单。使用用户已有材料，从最具体线索切入，已有证据足以回答时停止扩展。

## 功能或接口实现

用户从 UI 提问时，用 github-workflow 追踪页面、路由、hook 到 API，再沿后端 controller、service 找数据源及直接消费者。已有 endpoint 或后端实体时可直接从该处开始，不必先查前端。

需要解释引入背景时再查关联提交、PR 或 Jira。用户问所有页面入口时列出相关路由和数据源；问完整事件链路时，搜索事件、通知或 MQ 的发送点并回溯触发 API，核对新旧服务和消费者。

为后续方案调查现有能力时，先确认已有 API 是否提供所需数据、相邻页面是否有等价 hook 或公共能力，并核对语义与使用条件。是否新增后端能力由真实缺口决定，不预设纯前端或前后端联合方案。

## 字段或实体语义

用 github-workflow 查 DTO、proto、表定义，再追踪真实写入、转换和业务读取条件。区分生产路径与 generated、test、mock；PRD 中的 FINISHED 等用语不能替代真实 SQL 过滤条件。

代码无法回答实际取值或影响面时，再用 redshift 核对 schema、数据分布、统计范围及同步时效。需要历史意图时查 jira 或 lark-skills 中的引入记录。

对“和某接口一致”的描述，分别核对实体作用域、时间窗口、状态过滤及计算来源。同名或相近字段可能分别表示“没有完成预约”和“请求未带客户身份”，不能直接互换；协议默认 false 也不能证明业务判定已执行。

判断复用成本时，追踪 DTO 构造过程：字段可能由额外查询、聚合或实时计算得出，schema 中存在不等于其他链路可以直接取得。影响方案选择的口径冲突需连同来源和待决策事项交给后续方案，不擅自用当前实现替用户决定需求。

## 历史决策

从用户已有的飞书文档、Jira 工单或 Slack thread 开始，用 lark-skills、jira、slack 补齐讨论，核对时间、说明者职责、批准状态和适用范围。工程建议不自动等于产品决定。需要核对是否落地时，再通过 github-workflow 追踪关联 PR、提交及当前实现。

只有摘要或转述时，保留其中明确给出的陈述和来源关系，注明原文尚未核验；未读原文不等于摘要没有提供信息，也不能把摘要中的主张升级为已批准或已生效的事实。

读取与当前判断相关的设计截图、附件和被引用的评估材料，按对应底层技能获取并查看内容。评估材料中“复用某字段或方法”的建议仍需核对实际存在、生产写入、消费者和语义，不能只凭文档中的名称成立。

把“当时决定什么”“代码现在如何实现”“目标环境是否生效”分开回答，不能以其中一种证据替代其他两种。

## 线上情况

先固定目标环境、时间窗口和请求或业务实体。后端从 datadog 日志及 trace 起步；前端或客户端从 sentry 事件、版本和影响范围起步，不要求两者每次都查询。

需要统计影响面时，用 redshift 明确查询口径与数据延迟；需要使用行为时按需补充 posthog-skills。怀疑账号配置或灰度差异时，先确认配置所属系统，再按 [来源边界](source-boundaries.md) 选择 moe-mis、growthbook、posthog-skills 或 moe-grey，并关联运行证据。查询无结果时保留过滤范围与缺口，不把“未查到”当作“没有发生”。

## 客户报障与已知问题

先用 jira 读取 CS 工单、评论、附件及关联 Intercom 对话，提取客户原话、现象、时间、实体和已有排查结果。按具体症状检索历史相似工单，对比触发条件与 Cause and Solution，不因描述相似就认定同一根因。

需要解释现象时，再按已有 request ID、customerId、business 或版本去 datadog、sentry、github-workflow 查证。缺少某个来源时交付已支持的结论，指出最小补证信息。
