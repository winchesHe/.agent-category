# 来源选择与证据边界

只读取与当前命题有关的部分。这里负责选源和解释证据；具体接口、参数、认证与操作约束仍由对应技能负责。

## 使用行为与业务数据

- **posthog-skills**：回答功能使用、事件、漏斗与转化问题。先确认项目、事件及属性定义、用户或业务身份、时间窗口、去重方式和分母；区分埋点记录与真实业务完成状态。未采集到事件不证明用户没有操作，埋点中的金额也不能直接充当财务口径。
- **redshift**：按问题选择数仓或 MySQL/PostgreSQL 只读副本，先核对连接目标、schema、字段来源、生产链路和同步延迟。业务状态以实际表和过滤条件为依据；跨 PostHog 或报表对数时先统一实体粒度、时区、时间字段、状态及去重口径，再解释差异。

## 账号、配置与灰度

- **moe-mis**：用只读 profile 定位账号与 business/company/staff 的关系，用 Metadata 查询定位 Key、owner 类型、owner ID 和值。必须明确环境；默认配置、实体值和应用最终读取结果是不同证据。缺少登录上下文不自动授权 impersonate、临时密码或 OB 测试会话。
- **growthbook**：针对 GrowthBook 核对环境、feature、attributes 与 SDK 规则求值。管理端配置和对给定 attributes 的求值可解释规则，目标请求是否使用该配置仍需运行证据。
- **posthog-skills**：针对 PostHog Feature Flag 读取对应项目的配置与相关事件。不能用 GrowthBook 的配置或求值替代；要证明某用户实际拿到的值，需补充目标调用或运行记录。
- **moe-grey**：通过 list/get/branches 核对 namespace、规则和服务分支；由仓库或 PR 关联服务时，按该技能的 service mapping 核验 `svcBranchMap` key。规则存在、分支可选或映射已配置，都不单独证明目标请求命中该路由，应关联请求、Host、服务及版本证据。

用户只说“灰度”而未指定系统时，先从当前代码、配置引用或已有记录识别所属系统；不要假定三个系统等价，也不要默认全部查询。

## 测试、代码与交付状态

- **metersphere**：用用例、功能模块、评审和关联缺陷补齐预期行为及覆盖范围。用例存在或评审通过不等于测试执行通过；后者需定位执行结果、版本、环境和时间，没有相应入口或记录时明确缺口。
- **github-workflow**：当前代码、PR、CI 和部署记录分别回答实现、变更、检查与发布问题。CI 通过不等于已部署；部署记录也不能单独证明目标用户或请求已使用该版本。
- **moe-development**：需要仓库定位、开发约定或协议判断时使用开发路由，按需读取本地开发经验。单仓调查不加载无关协议与依赖判断；调查只取证，不自动触发代码修改、代码生成、联调、发布或经验写入。

## 客户报障与原始对话

客户单点报障从 jira 的 CS 工单及关联 Intercom 对话起步。相关协作讨论按 slack 的既有入口查询，飞书原文用 lark-skills。

同一客户反馈可能被转为 Jira 工单或复制到 Slack。以来源允许使用的原始记录链接、工单关联和实体时间线去重，不为去重额外提取底层技能禁止传播的字段；关联不足时保留不确定性，不把转述次数当作独立客户数。

## 与执行技能交接

moe-opc、flow 系列、moe-release-ticket、moe-use-web-ui 等负责相应设计、实现或交付目标，不是普通上下文调查的必跑依赖。review-brief、writing-charter 等按用户需要组织交付产物。已有任务明确授权后续工作时，携带可定位证据、假设和未解决项继续对应流程；不能把收集到的操作建议当作新增授权。
