# 整体 Review 总结

最终审查输出需要回答“这次改动整体上怎样、关键边界在哪里”，而不只是列出问题。
本参考在主 agent 完成 finding 复核后使用；不新增一次全仓探索，不让 reviewer 各写一份
重复总结。这里定义内容，GitHub 发布权限和传输由 github-workflow 负责。

## 组织方式

根据实际复杂度选择短段落或“总体判断 + 少量分组要点 + 结论”。通常先用 2–4 句话
说明本次目标如何落到实现、关键链路和主要设计判断。存在跨组件问题时，再按共同原因
组织要点，避免按文件清单或问题编号复述。简单修复不必填满所有类别。

总结应按证据回答适用的问题：

- 主要行为如何串起来，哪些职责、状态边界或协议承担了关键约束？
- 当前设计哪些部分已有一致的规则或合理的隔离？哪些共同问题值得在本次统一处理？
- 需要调整的是领域规则、API 映射、状态流转还是展示组件？修复应止于什么边界？
- 哪些重复或差异具有合理原因，可以保留？哪些非阻断演进建议值得后续考虑？
- 已知缺陷和未覆盖范围对整体结论有什么限制？

不要套“整体功能比较完整，但……”等空泛开场。设计评价需要能指向已读代码、symbol、
契约或调用链；不能从文件数多、测试文件存在或 reviewer 无 finding 推断整体质量良好。
肯定性判断同样要限定范围，例如“提交入口和回调复用同一状态转换函数”，比“架构很好”具体。

## 建议强度与证据

“本次必改 / 非阻断建议 / 可以保留”用于表达设计边界，不是另一套问题优先级，
不必固定作为三个标题，更不要求每类都有内容。

| 总结内容 | 证据要求 | 与结论的关系 |
|---|---|---|
| 本次必改或阻断性设计要求 | 对应已核实的 P0–P2 finding，写清共同原因与受损场景 | 与 findings 一致，不在总结里另造阻断项 |
| P3 问题的共同原因 | 仍须满足完整 finding 门禁 | 明确非阻断，不升级为必须重构 |
| 演进建议 | 有具体 symbol、约束或取舍作为依据，明确收益及代价 | 不计入 finding 数量，不单独改变 verdict |
| 可以保留的实现 | 说明其语义差异、既有边界或扩大改动的代价 | 限定本次修复范围，不等于证明该实现不存在其他问题 |
| 未决设计问题 | 有来源且答案会改变结论 | 标为 open question，澄清前不给 merge verdict |

缺少证明的缺陷断言不能改名为“整体建议”绕过门禁。若建议复用现有能力，仍需指出
具体复用目标、语义相容性与分化风险。若写“必须统一”，先检查是否真的有阻断 finding
支持；仅仅相似或风格偏好不构成要求。总结发现新缺陷时，回到 finding 核验流程。

设计建议不得默认扩大为跨系统重构。可以明确“本次只统一领域规则，保留两套展示组件”，
但必须有已审查的职责差异或修复范围证据，不能照搬示例到其他项目。

## 与 inline、渠道和 verdict 的关系

- Findings 负责离散问题的定位、触发条件、影响和修复方向；总结负责综合判断和边界。
  总结可关联对应 finding 或已提交的 inline 链接，不逐段复制其内容。
- 对话结果仍按主文档先 findings、再未决问题与覆盖说明、最后整体分析；GitHub review
  body 则直接使用整体分析，具体 findings 由 inline 承载。无法绑定合法 diff 行时，
  明确说明并保留可定位的问题描述，不伪造 inline 定位或声称已经发布。
- Slack 回执可以只放结论与链接。GitHub 总结不能只剩数量、等级、“详见 inline”。
- 完整覆盖且结论明确时沿用主文档 verdict；只有 P3 仍为非阻断，普通演进建议不新增
  Request changes。没有 finding 时不强行制造改进项。
- 局部或静态审查也可以有整体分析，但“整体”仅指已授权范围，不能暗示审完了整个 PR；
  缺失覆盖、未运行验证和会改变结论的未决问题必须保留。审查完整性不能靠措辞补足。

## 示例

以下为虚构证据包的表达示例，不是对某个真实 PR 的判断或固定模板。

### 跨组件设计与已核实缺陷

前提：审查已确认提交和预览各维护一份状态规则，其中一份漏了取消状态，构成 P2；
两套展示组件分别承担不同布局与交互，未发现本次修改导致的展示缺陷。

```markdown
本次改动把取消状态接入了筛选和提交流程，但两条链路各自维护状态规则，预览与实际提交
在取消场景下不一致。整体上需要统一的是状态语义，而不是把两套页面一起重写。

- **本次需要修正**：将提交与预览的取消状态判断对齐到已核实的领域规则；具体漏判场景
  见对应 inline comment。这是同一业务语义在不同入口分化的问题。
- **可以保留**：两套展示组件承担不同布局和交互。本次缺陷修复无需合并它们，避免扩大
  回归范围；共享边界应停在状态规则，而非整条渲染链路。

当前结论为 Request changes，依据是上述已核实的行为不一致。
```

### 只有非阻断问题

前提：完整审查发现一个 P3 重复查询，有边界且当前无关键延迟影响；两个入口已复用
同一鉴权函数，其余未发现需要阻断的问题。

```markdown
两个入口复用同一鉴权规则，本次变更的权限边界保持一致。可改进处是详情加载中重复执行
相同查询，具体调用位置见 inline comment；该问题当前有明确请求次数上限，属于非阻断项。

建议后续在这条调用链内复用已取得的数据，不需要为此增加跨请求缓存及其失效机制。
结论为 Approve with non-blocking comments。
```

### 无 finding 或局部范围

无 finding 时说明核对过什么，例如“这次修改将空值规范化集中到提交边界，两个调用方
沿用相同的删除语义；在完整 PR 范围内未发现实质问题。结论为 Approve。未运行集成验证。”

若只审查提交边界，则应改成“在已审查的提交边界内未发现实质问题；其他调用方尚未覆盖，
不能据此给出整个 PR 的合并结论”。不能保留前一句的“完整 PR”和 Approve。
