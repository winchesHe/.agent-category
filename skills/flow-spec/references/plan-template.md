# plan 文件模板

使用方式：起草 `docs/plans/<slug>.md` 时按本模板填写。

**仅在 spec 的 4 指标命中 ≥ 2 时建议创建**（命中 < 2 → 跳过 plan，只 spec）。

**plan = 子模块级描述性设计 + Chunk 化执行节奏**：含关键设计（行为 / 流程 / 状态机）+ Chunk 划分 + Observability Checkpoint + Y-only 活更新。

## 多 plan 命名（可选）

一个 spec 含多个子模块时，拆多份 plan：

- `docs/plans/<slug>-01-<子模块>.md`
- `docs/plans/<slug>-02-<子模块>.md`

单一子模块时 `docs/plans/<slug>.md` 即可。

## 模板

````markdown
# <task-slug> — Plan

> 实现节奏 + 关键设计。完成后由 `flow-ship` 归档到 `docs/plans/done/`。
> spec：`docs/specs/<slug>.md`

## 目标

对应 spec `§ 后续实现顺序` 中的某子模块 / 步骤。让 <具体能力> 可用。

## 最小可验证链路

```bash
<cli> command --arg
```

期望输出 / 行为：

```text
...
```

## 关键设计

**子模块行为 + 流程描述**（描述性，不嵌代码 / 伪代码 / 接口签名——接口签名在 spec `§ 接口设计` 已有）。

- **行为**：<做什么 / 解决什么>
- **处理流程**：1. ... 2. ... 3. ...
- **状态机 / 状态转移**：<...>
- **命令链 / pipeline**：`<cli-a> | <cli-b>`
- **业务输入输出**：<字段名 + 含义，无类型注解>
- **模块间调用关系**：<文字 A → B → C>

## 实施者警告（按需，仅多 Chunk 含中间 broken 状态时写）

- **中间状态会 broken**：Chunk 1-N 期间 `pnpm tsc --noEmit` / 全仓测试会失败 —— 预期，不要慌
- **推荐验证节奏**：每个 Task 只跑本任务覆盖的测试文件（如 `pnpm vitest run <path>`）
- **第一次跑全仓**：在 Chunk N 完成后

小 plan（单 Chunk / 无中间 broken）省此段。

## Chunk 划分

### Chunk 1: <主题>

| # | 步 | 观察点 | 验证方式 | 状态 | reviewed |
|---|---|---|---|---|---|
| 1.1 | <端到端最小骨架> | <UI / 日志 / metric> | <命令 / 断言 / 视觉> | ⏳ | —— |
| 1.2 | ... | ... | ... | ⏳ | —— |

**Observability Checkpoint**（Chunk 1 末尾必有）：

- **运行命令**：`<smoke-cmd>` / `<verify-cmd>`
- **期望输出关键字**：`[CHUNK 1]` / `<expected-string>`
- **失败常见根因**：<...>

### Chunk 2: <主题>

（同上结构）

## 风险点 + 兜底

- <风险> —— <粗描述兜底方向>

## 验收

子模块完成后必证：

```bash
<verify-cmd>
```

必须证明：

1. ...
2. ...

## 非目标

本 plan 范围内明确**不做**的事。

## 决策记录（活更新，Y-only）

每步完成时：
- 步骤节奏表 reviewed 列填 `YYYY-MM-DD`（**无论 Y/N**）
- **仅当对后续步有影响（Y）时**追加段：

### 步 N.M 完成（YYYY-MM-DD）
- **影响**：<拆 / 删 / 调整哪些后续步>
- **新发现的事实**：<...>
````

## 字段说明

### `## 目标`

对应 spec `§ 后续实现顺序` 中的某子模块。一段话讲做什么 + 验收什么能力。

### `## 最小可验证链路`

CLI 命令 + 期望输出 / 行为。能直接跑、能看到效果。

### `## 关键设计`（子模块行为 + 流程描述，**不嵌代码**）

| ✅ 写 | ❌ 不写 |
|---|---|
| 子模块行为描述（做什么 / 解决什么） | 完整代码 / 函数实现 |
| 处理流程（文字步骤） | 伪代码 |
| 状态机 / 状态转移 | TypeScript / Go types（spec `§ 数据模型` 已写） |
| 命令链 / pipeline（文字描述） | 接口签名（spec `§ 接口设计` 已写） |
| 业务输入输出（字段名 + 含义，无类型注解） | UI 像素 / 完整 SQL body |
| 模块间调用关系（文字 A → B → C） | 测试代码 |

**关键设计 ≠ spec 重复**：

- **spec**：全局接口签名 + 数据模型 + 架构（**含类型 / 代码**）
- **plan 关键设计**：子模块级**行为 / 流程 / 状态机**（**纯描述，不嵌代码**）

### `## 实施者警告`（按需）

仅多 Chunk plan + 含跨 Chunk broken 状态时写。明示中间不要跑全仓 X / 推荐验证节奏 / 第一次跑全仓的时机。

单 Chunk plan 省此段。

### `## Chunk 划分`

把"步骤节奏"按主题分 Chunk：

- **单 Chunk plan**：直接一个 `## 步骤节奏` 表（不必加 Chunk 标题）
- **多 Chunk plan**：每个 Chunk 一个 `### Chunk N: <主题>` + 步骤节奏表 + Observability Checkpoint

**Chunk 划分原则**：

- 一个 Chunk = 一个可独立验收的中间态（Observability Checkpoint 可跑通）
- 单 Chunk 内 step 颗粒度 1-2 次会话内完成
- Chunk 之间允许中间 broken（在实施者警告里明示）
- **不强求 step 行数上限**（每步颗粒度由 agent / 用户判断）

**步骤节奏表列**：

| 列 | 说明 |
|---|---|
| `#` | 步序号（多 Chunk 时用 `N.M`，N=Chunk M=step） |
| `步` | 端到端最小骨架 / 可独立验证的小改动 |
| `观察点` | 怎么看到效果（UI / 日志 / metric / 数据查询） |
| `验证方式` | 怎么知道对错（命令 / 断言 / 视觉对比 / 测试） |
| `状态` | `⏳` → `✅` |
| `reviewed` | `YYYY-MM-DD`（每步完成必填）/ `——` |

**步设计原则**（来自 user CLAUDE.md）：每步**能跑、能观察、能验证**；端到端最小骨架作为**步 1.1**；1-2 次会话内完成。

### `## Observability Checkpoint`（多 Chunk 必有，单 Chunk 可选）

每 Chunk 末尾的可验证回路（命令 + 期望关键字 + 失败根因）：

- **运行命令**：可直接跑的 smoke / verify 命令
- **期望输出关键字**：能让人 / agent 肉眼判断"过了"的关键字
- **失败常见根因**：列常见出错点 + 排查方向

### `## 风险点 + 兜底`

潜在问题 + 粗兜底方向。**不写代码方案**。

### `## 验收`

子模块完成后必证的命令 + 事实清单。

### `## 非目标`

本 plan 范围内明确**不做**的事。

### `## 决策记录（活更新，Y-only）`

flow-impl 每步完成时：

1. **无论 Y/N** → reviewed 列填日期（agent 已 sanity-check 是否影响后续步）
2. **仅 Y 时** → 追加决策段

Y-only 防 yes-noise 化。

flow-ship 归档前校验（**3 项全过**才准入）：

| 检查项 | 通过条件 |
|---|---|
| 步骤节奏表 | 全 ✅，无 ⏳ |
| reviewed 列 | 每行非空 |
| 决策记录段 | Y 步对应 ✅ 行有决策段（N 步不需要） |

## 关键约定

- **无 frontmatter**：plan 是普通 markdown
- **plan 写描述性子模块设计**（行为 / 流程 / 状态机）；spec 写全局产品设计图（含接口签名 / 数据模型 / 类型）；**两者不重叠**
- **plan 不嵌代码 / 伪代码 / 接口签名**（接口签名 / TypeScript types 在 spec `§ 接口设计` 已有；代码本身在 implement 阶段）
- **不强求 step 行数上限**（由 agent / 用户判断，参考"1-2 次会话内完成"原则）
- **多 Chunk 必有 Observability Checkpoint**（命令 + 期望关键字 + 失败根因）
- 完成后 `flow-ship` `mv` 到 `docs/plans/done/<slug>.md`（保留历史，不删除）
- 大需求拆多份 plan：`<slug>-01-<sub>.md` / `<slug>-02-<sub>.md`
