# 问题定义与重构方法论

当用户不清楚自己真正要解决什么问题时，使用这些方法帮助他们从模糊走向清晰。

---

## 1. 分层追问（Iceberg Model）

问题像冰山，表面可见的只是事件，底下有层层结构。逐层下探：

| 层级 | 追问 | 目的 |
|------|------|------|
| **事件层** | 发生了什么？具体场景？ | 锚定讨论的事实基础 |
| **模式层** | 这是第一次还是反复发生？有无规律？ | 区分偶发 vs 系统性 |
| **结构层** | 什么机制/流程/激励在驱动这个模式？ | 找到杠杆点 |
| **心智模型层** | 什么信念/假设让人对这个结构视而不见？ | 找到最深层的卡点 |

**使用时机**：用户描述了一个表面现象但直觉感觉"不对"却说不清为什么。

**实操要点**：
- 不需要每次都挖到最底层——有时候在结构层就能找到足够的洞察
- 每层之间的追问用"为什么这个模式会存在？"来过渡
- 如果用户在某一层突然犹豫或情绪变化，那里往往就是关键

## 2. 问题重构（Frame-Storming）

来自 HBR 的 E5 框架。核心洞察：**brainstorming 生成的是解决方案，frame-storming 生成的是问题的定义本身**。大多数时候人解决不了问题，不是因为缺乏解决方案，而是因为问题定义错了。

### 重构手法

**换主语**：
- "如果这不是你的问题而是你的用户/老板/竞争对手的问题呢？"
- "谁最受这件事影响？从他们的视角看，问题是什么？"

**换时间尺度**：
- "一年后这个问题还重要吗？"
- "如果给你三年而不是三个月，你会怎么定义这个问题？"
- "五年前这个问题存在吗？什么变了？"

**换抽象层次**：
- 上升："更高一层看，这属于什么类型的问题？"
- 下降："能给我一个最具体的例子吗？"
- 横移："这让你联想到什么别的领域的问题？"

**反转法**：
- "如果我们故意让这个问题变得更严重，要怎么做？"
- "什么情况下这个'问题'反而是个优势？"
- 反转常常揭示真正的因果链和杠杆点

**极端假设**：
- "如果你有无限资源，你会怎么处理？"（去除资源约束看本质）
- "如果你完全没有预算，你会怎么处理？"（发现什么是真正核心的）
- "如果必须在24小时内解决呢？"（强制优先级排序）

### E5 完整框架

1. **Expand（扩展）**— Frame-Storming：生成多个问题定义的替代方案
2. **Examine（审视）**— Iceberg Model：逐层探查根因
3. **Empathize（共情）**— 利益相关者映射：Say/Think/Feel/Do 四象限
4. **Elevate（提升）**— 四视角检验：结构、人、政治、文化
5. **Envision（展望）**— 回溯法：从期望的未来状态倒推路径

**注意**：这五步不是线性流程。根据情况从任何一步切入，循环使用。

## 3. 问题空间 vs 解决方案空间

来自 Design Thinking 的 Double Diamond 模型。

### 核心区分

| | 问题空间 | 解决方案空间 |
|--|---------|-------------|
| **目的** | 理解要解决什么 | 决定怎么解决 |
| **活动** | 发现、定义 | 开发、交付 |
| **语言** | 需求、痛点、障碍、为什么 | 功能、方案、实现、怎么做 |
| **风险** | 过早收敛（漏看了真问题）| 方案脱离真实需求 |

### 过早跳入解决方案空间的信号

- 用户在描述问题的时候用了解决方案的语言（"我需要一个XX系统" vs "用户在做YY的时候会卡住"）
- 讨论还在第一分钟就已经在谈"怎么做"
- 用户反复回到同一个方案但说不清为什么选它
- 用户说"我试过了但不行"——可能是方案不对，也可能是问题定义不对

### 帮助用户留在问题空间的话术

- "等一下——在讨论怎么做之前，我想确认我们对'为什么'的理解是一致的。"
- "你描述的是一个解决方案。它在解决什么问题？那个问题还有没有别的解法？"
- "如果你的这个方案完美实现了，用户获得的是什么？那个'什么'才是问题。"

## 4. 约束 vs 假设分离

帮用户区分什么是不可改变的现实（真约束）和什么是看似约束但实际可挑战的假设。

### 操作步骤

1. **列出所有的"不能"和"必须"**
   - 让用户穷举所有他认为的限制条件

2. **逐一分类**：
   - **硬约束**：物理定律、法律法规、不可逾越的资源上限
   - **软约束**：组织惯例、历史决策、"一直这么做"的习惯
   - **假设**：未经验证的信念，包装成了约束的模样

3. **挑战软约束和假设**：
   - "这个限制是谁设定的？设定的原因现在还成立吗？"
   - "如果违反这个约束，最坏后果是什么？我们能承受吗？"
   - "有没有人已经成功违反过这个'约束'？"

4. **重新定义问题**：
   - 去掉假约束后，问题的解空间通常会显著扩大
   - 被假装成约束的假设——这通常就是创新空间所在

### 常见的假约束

- "用户不会接受这种改变" → 实际测试过吗？
- "技术上做不到" → 是做不到还是比较困难？
- "预算不够" → 是真的不够还是优先级排列的问题？
- "时间不允许" → 是绝对截止日期还是人为的节奏？
- "行业里从来没人这样做" → 所以？

## 5. "How Might We" 问题构造

将问题陈述转化为开放式的"我们如何可能..."句式，作为从问题空间到解决方案空间的桥梁。

### 构造规则

- 足够宽泛以允许多种解法
- 足够窄以提供方向
- 不暗示任何特定解决方案

### 变体技巧

从一个基础 HMW 生成多个变体：
- **放大**："我们如何可能让这个效果10倍放大？"
- **缩小**："最小可行的版本是什么？"
- **反转**："如果我们故意让用户体验变差，该怎么做？"（然后反转每一个让体验变差的行为）
- **换角色**："从[其他利益相关者]的角度，HMW是什么？"
- **分解**：把一个大HMW拆成2-3个子HMW

### 使用时机

当问题已经被充分理解（走过了问题空间的发散和收敛），准备进入解决方案空间的发散阶段时。HMW 是两个钻石之间的桥梁。
