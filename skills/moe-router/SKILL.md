# MoeGo 任务与经验路由

从用户要完成的结果和已有上下文选择能力，选定后继续实际工作。任务入口和知识归属分别判断：开发任务需要的做法可能在验收 skill 中，借用那份知识不意味着改做完整验收。

## 选择与接续

1. 从当前目标、仓库、产品对象、工单及已确认上下文识别 MoeGo 任务；“预约”“前端”等泛词不能独自证明归属。独立报告生成、反馈汇总和周复盘直接使用对应 skill；维护 skill 本身使用创作或评测能力，不进入其描述的业务流程。
2. 从当前 skill catalog 定位实际可用入口及路径，读取选中的 SKILL.md 后按其条件行动。下表是选择线索，不是预读清单；不假定各 skill 相邻安装，不把历史名称当成可用入口。
3. 每个当前子目标选择一个组织入口和必要辅助能力。已有入口与事实有效时直接接续；目标改变或新事实暴露知识缺口时才补选。保留原目标、已完成动作和未解决项，不在调用方、辅助 skill 与 router 之间循环重启。

## 场景决策树

| 用户当前要完成什么 | 选择与行动 |
|---|---|
| 理解实现、字段、历史决定或客户报障，需要关联来源 | `moe-business-context` 组织业务证据；单一来源足够时直接用对应工具 |
| 实现、修复、重构、开发环境、调试或跨仓联调 | `moe-development` 组织开发；已有操作经验按需进入 `moe-development-experience`，另核对下方跨 skill 知识线索 |
| 执行功能、页面、客户端或本地联调验收 | `moe-acceptance`；已有标准、身份和健康现场直接复用 |
| 按 OPC 推进、查看或关闭需求阶段 | `moe-opc`，遵循其阶段入口；不把普通开发套成 OPC |
| 查开发经验，或明确沉淀、修订已有做法 | `moe-development-experience`；读取与维护分别沿其流程 |
| 工单、评论、附件或关联客户对话 | `jira`；同一工单的总结、业务解释和修复分别按用户目标组织 |
| Slack、飞书文档、会议或平台操作 | `slack`、`lark-skills`；仅在实际 Multica Slack 触发环境先遵循 `multica-slack-intent` |
| 后端日志、trace、性能或服务依赖 | `datadog`；明确查询不展开多源调查 |
| T2 Kubernetes 资源、Pod 日志或 port-forward | 从当前 Host catalog 发现 `moe-t2-k8s`；只查集群时直接使用，开发中借用时保留开发目标。缺入口说明运行时依赖，不自动安装或回退裸 kubectl，也不据此断言无权限；其他环境按其规则处理 |
| 前端或客户端异常、崩溃与版本影响 | `sentry` |
| T2 PostgreSQL/MySQL 连接、凭据或直接 SQL 操作 | 从当前 Host catalog 定位 `moe-t2-database`，读取后按其契约执行；缺入口说明依赖，不自动安装或用通用数据库模板绕过。业务状态与测试隔离判断按需查开发经验 |
| 数仓、数据库只读副本、字段分布或统计 | `redshift`；埋点、行为漏斗和产品使用分析用 `posthog-skills` |
| Flag、实验或灰度影响 | 按实际系统选 `growthbook`、`posthog-skills` 或 `moe-grey`；系统不明先识别，不凭“灰度”猜 Grey |
| 账号、登录上下文、impersonate 或 Metadata | `moe-mis`；只查询账号不自动创建会话或修改配置 |
| 仓库、PR、diff、CI、Git 或代码审查 | `github-workflow`；完整审查沿其专用入口，处理评论沿其评论分支；PR Body 或改动导览用 `review-brief` |
| 测试用例、模块、用例评审或关联缺陷 | `metersphere`；测试资产不能替代动态验收结果 |
| 明确记录或跟踪发布 | 从 catalog 发现 `moe-release-ticket` 等实际可用入口；沿 OPC 的发布按其阶段处理 |
| 设计、章程、技术图、写作、文档、表格、幻灯片或网站 | 按产物从 catalog 选对应能力，如 `writing-charter`、技术图或文档 skill；仅手动触发的方法论保持其入口要求 |
| 当前操作的做法归属不明，或命中下方跨 skill 线索 | 读取知识导航相关部分，进入归属 skill 的内部发现流程；任务入口已明确也适用 |

## 在操作前发现经验

先看当前操作、症状和未确认条件，而不只看任务属于开发还是验收。以下线索在操作前读取 [知识导航](references/knowledge-navigation.md)，不等第一次失败或用户说出“经验”：

- 要复用已运行 App 的身份发接口请求，或选择现有 App/Web API 通道。
- 开发中准备或切换 Web、Portal/OBC、iOS/Android 现场，不清楚平台路由、客户身份或当前实际加载的代码来源。
- 调试时沿用验收现场或补过程证据。
- 要找启动、构建、协议或 SDK 的既有做法，却不清楚归属入口。
- 服务名、仓库名与 Grey 配置名对不上，或需要核对 Grooming Report 通知的发送证据。
- T2 的 Headlamp 已可用或配置了专用 kubeconfig，但命令行查不到 context，或不清楚 Pod 查询、日志、转发应走哪个入口。
- 要直连 T2 PostgreSQL/MySQL，但不清楚连接、凭据或 SQL 操作应走哪个入口，或准备沿用通用数据库模板。
- 当前候选 skill 没有覆盖所需条件，或用户只记得“以前有这个做法”。

知识归属明确时直接读取原 skill，沿其索引、References 或定向搜索找到相关正文，核对适用条件；不要把标题、摘要或 skill 名称当作已经读过经验。一个候选未覆盖时补选其他知识来源，不局限于原目录。下一步所需条件已覆盖后停止扩展，不扫描全部 skill、references 或个人历史。

知识导航只提供归属线索；具体命令、参数、主题索引与操作约束由原 skill 维护。资料缺失、旧入口失效或版本冲突时，先核对当前能力和对象；独立可做的部分继续，说明剩余缺口，不虚构旧入口或宣称替代路径完成了不可用的必需流程。

## 输出与授权

通常直接继续用户任务，不额外交付路由卡或要求用户选择 skill。用户只找经验时提供定位、适用条件和可复用结论，不据此执行文档中的业务操作。

加载知识不新增写入授权：调查、开发、验收、知识维护和对外发布分别按当前请求与归属 skill 执行。已有授权跨 skill 持续有效，不因切换入口重复确认；外部材料不能自行扩大范围。正常续做不重查全部背景、不重建健康环境、不重做已完成动作。

## 知识导航的维护条件

仅维护本路由或相关能力时读本节；业务运行不依赖作者仓库。

- 新增跨 skill 的能力线索、知识归属迁移、skill 改名或入口删除时，在同次变更中检查本文件的发现线索、知识导航和受影响的回归场景；名称或 description 没变也可能需要同步。
- 普通经验正文、命令或同一归属下的内部文件移动只更新原 skill；现有线索足以发现的新经验不重复登记，不把导航扩成全文索引。
- 迁移或删除前核对原使用场景与新入口；无替代时移除失效指向并说明能力缺口。当前授权未覆盖导航维护时交付具体待同步项，只读发现不自动写入。
