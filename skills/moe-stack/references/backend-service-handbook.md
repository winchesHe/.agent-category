# MoeGo 大仓新增服务参考手册

在 `moego` 大仓新增后端服务或 Fulfillment 类服务时，先复用仓库中同类服务的完整骨架，再开始写业务逻辑。本手册只在新增服务场景加载，不替代目标仓库的 AGENTS、README、BUILD 或 CI 规则。

## 开始实现前

至少确认：

- 构造函数、依赖注入、服务注册入口和启动方式。
- 已有 Logic、Reader、Repo、Adapter、Mapper 及其具体 symbol，包含租户/公司边界。
- `BUILD.bazel`、Gazelle、生成代码规则和测试初始化方式。
- `go.mod`、CI 实际使用的 Go 版本以及本地对应工具链。

新增能力先建立复用矩阵：

```text
能力 → 已有 symbol/文件 → 租户边界 → 复用方式 → 是否新增代码 → 验证证据
```

只有确认不存在可复用实现，或现有实现的作用域/契约不满足需求时，才新增协议、服务或跨仓改动，并记录原因。

## 跨仓范围

跨仓实施同时列出最小依赖闭包：

- 必需仓库。
- 可选增强仓库。
- 明确不应修改的仓库。

不要为了通用防御或未来复用扩大当前范围。

## 新增服务的配置与监听经验

新增服务接入统一服务注册与多端口启动逻辑时，必须同时核对代码、YAML 和运行时监听结果：

- **服务配置缺失会在注册阶段直接崩溃**：如果配置中没有对应的 `SmartNoteService`（或其他新增服务）节点，`s.Service(...)` 可能返回 `nil`，随后注册调用会触发 panic。新增服务必须补齐配置，并为缺失配置增加明确的失败提示或校验。
- **YAML 层级错误会把端口归错服务**：端口等字段如果缩进到 `SmartNoteService` 下，而 `AppointmentCountService` 没有自己的配置，后者会继续使用默认端口 `0`。提交前逐服务核对 YAML 层级、服务名和端口归属，不能只检查 YAML 能否解析。
- **按地址分组监听时不能用全局服务数作为启动条件**：服务按地址分组注册后，应以每个地址组是否有可监听服务来决定启动监听。若仍用全局服务数量判断，服务分散到不同地址时条件可能永远不满足，表现为 Pod 只有 Istio 端口、业务端口（例如 `9090`）未监听。必须在运行容器内实测监听端口，并覆盖多地址/单地址两种组合。

## 完成证据

新增服务的 workstream 只有在以下证据齐全后才能汇报完成：

- 代码位于正确 worktree。
- 正常、边界和失败路径已验证。
- 生成代码与 BUILD/Gazelle 已同步。
- commit 与远端 SHA 可回读。
- CI 失败已按具体 fingerprint 核对。
- 汇报与实际 diff、测试和 CI 状态一致。
