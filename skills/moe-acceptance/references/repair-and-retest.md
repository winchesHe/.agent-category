# 调查、修复与局部复验

[主文件的问题处理入口](../SKILL.md#验收途中遇到问题)负责选择下一步。本文件仅在调查方法、代码来源、更新方式、构建/部署等待或复验起点需要展开时读取；账号、数据和平台恢复方法仍在各自 reference 中。

## 选择调查动作

| 当前信号 | 下一步最小动作 |
| --- | --- |
| 业务断言与标准不符 | 结合页面、当前输入、相关响应和代码定位业务差异 |
| HMR 后未见对应更新 | 有界等待开发服务或页面实际信号，必要时刷新当前 tab |
| 请求连接失败 | 检查受影响服务；确有需要才重启该进程 |
| 401、身份不匹配 | 暂停依赖该身份的动作，确认账号/环境并恢复对应登录 |
| Host 或本地路由异常 | 检查该 session 的路由与受影响服务，不重置无关数据 |
| 当前数据不存在 | 查询可复用数据，只补当前前置 |
| tab 损坏 | 最小页面恢复，确认不可用才替换上下文 |

这些是需要补证时的选择线索，不是逐项检查清单。已有证据足以定位原因时直接处理；环境修复使用现有组件的真实工具合同，不假设 bridge 有未实现的组件子命令。

## 调查动作与记录

需要展开调查时，用以下信息支持下一步判断；已有事实直接复用，只补当前缺口。记录方式沿用主文件，凭据和未经检查的完整响应不进入记录。

| 记录内容 | 判断用途 |
| --- | --- |
| 受影响 Case、实际错误和候选原因 | 区分已观察事实与待验证假设；通用错误页不能直接确定根因 |
| 路径及选择依据 | 说明该动作能区分哪些原因，为什么当前值得执行 |
| 实际动作、结果和证据引用 | 写清得到什么新信息、排除了什么；未执行的建议不算尝试 |
| 下一步或排除原因 | 对尚未执行的适用路径，说明继续动作或不能执行的具体依据 |

优先获取能区分原因的具体错误、相关日志或请求结果；工具不支持时记录能力限制并寻找适用替代。原因尚未明确，且已有可比的成功平台或环境时，优先利用相关代码来源、配置、请求和加载链路的差异缩小调查范围，不重跑无关成功 Case，也不预设差异就是根因。已有证据足以定位原因时，直接处理对应问题。

同一假设下换地址、刷新或重试，只在得到不同证据时才扩大已排除的范围，不能以次数证明原因已查尽；假设未变也不妨碍执行尚未尝试、能区分原因的检查。

记录须能支撑[主文件的继续、暂停与结束判断](../SKILL.md#继续暂停与结束)，而不只是罗列未执行的建议。

## 实际消费入口与来源

已知且可靠的来源事实直接复用；需要确认本地代码或选择修改位置而来源有歧义时，才补最小只读观察。静态路由、import、sourcemap 文件名和 bundle 含某模块只是候选；正确 Host、200、启动 cwd 或页面标题不能单独证明当前页面消费了目标代码。

按当前工具实际能力选择一条充分路径：例如业务动作的调用栈/initiator 定位实际模块，再将页面已加载的相关源码与目标 worktree 核对；或可信构建来源标识配合实际挂载分支。不是 UI/DOM/Network 固定多证门禁；先查工具合同，不编造探针。

来源绑定包含可确认版本和目标相关未提交改动，commit 不能覆盖 diff。相同源码内容不能反推唯一 commit；只能证实内容一致就如实限定，若目标要求区分构建仍是信息不足。可靠证据显示错误分支、非目标代码或远端回落则是不通过；缺实际消费或来源证据是信息不足，不能改文案、touch 文件或制造 HMR 来凑证明。

入口确认、HMR 连续性和业务修复分别给结论；入口通过不额外证明后两项，也不抹掉独立业务 case 的观察。没有真实缺陷就不制造修复。

## 代码修复

1. 在刷新、修改或关闭可能消除差异前，保留 Claim 所需的 before 或瞬时证据。
2. 查看 worktree 状态和已有 diff，理解相关实现；只修改当前需求范围，保留用户改动。
3. 按改动与实际消费方式更新代码：支持热更新的 Web/原生 JS 使用 HMR 或 Fast Refresh；原生依赖或配置变化按平台 reference 构建并安装；本地后端按项目方式更新受影响进程；测试环境部署按 moe-development 准备，再接下方等待指引。已有授权的提交、推送或部署若是验收前置，先完成前置再验收。依据实际信号有界等待，不轮询文件树或无条件固定睡眠。
4. 确认相关新代码已加载；缺信号则记为未确认，页面仍可访问或 touch 文件不够。
5. 按下方[恢复后的复验范围](#恢复后的复验范围)继续原 Case；共享代码影响另一 session 时，让其单独确认受影响观察。

## 等待构建或部署后续验

本次验收依赖的构建、CI 或部署仍在执行时，使用 github-workflow、moe-development 或对应平台的已有能力查看实际进展。记录具体 run/部署引用、目标 SHA 或可确认版本、目标环境、满足条件及下一步 Case；这些是当前任务的恢复线索，不新增状态管理系统，也不扩大部署、重试或配置写入授权。

在当前运行能够继续等待时，按工具支持有界等待实际对象并查看新增进展，等待期间保留健康身份、页面和数据，不仅回复“等待部署”就结束工作。CI 成功与目标环境已部署分别判断；确认目标版本就绪后，继续核对实际流量或页面消费来源，再执行受影响 Case，不需用户另行提醒。旧版本成功、其它分支部署成功或仅有任务状态变化不能满足本次条件。

出现失败项时，先判断它是否阻断本次目标版本的部署、实际消费来源确认或当前 Case。目标版本已成功部署且相关验收前置成立时，与部署和本次验收无关的 lint 或其它检查失败只记录为独立检查结果，直接继续验收，不为等待 CI 全绿而停住，也不顺带修复这些失败。不能仅凭 workflow 总体失败或检查名称判断影响；必要时核对相关 job 和部署事实。

实际阻断当前验收的失败按[主文件的问题处理入口](../SKILL.md#验收途中遇到问题)选择下一步；需要暂停等待时保留上述对象、条件及最后一次观察。外层调度器若已配置，负责运行结束后的条件检查和唤醒；Skill 不自行创建定时任务，也不在未配置时承诺自动恢复。

Figma UI 差异的修复计数与停止边界见 [UI 走查](ui-design-review.md#修复复验与停止)；复用本文件的更新及来源确认方法，不以一次视觉差异结束可继续修复的 Case。

## 恢复后的复验范围

连续性只证明新 UI/模块信号、同一页面和登录态保持。业务修复还需真实相关代码变更和业务动作、断言；无关 placeholder 或样式更新不能证明筛选/提交修复。

记录实际差异、恢复或代码改动，以及哪些输入、步骤和观察因此失效，据此选择最早复验点。只补受影响的前置，再实际执行目标动作和断言；仍有效的身份、数据、tab 与已完成证据直接复用。具体动作语义和业务三态见 [case-execution](case-execution.md#观察与结论)。没有真实 bug 不修改业务逻辑制造修复。
