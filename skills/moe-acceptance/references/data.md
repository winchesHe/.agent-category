# 业务数据与测试配置

按当前请求或 case 的实际缺口使用现有 Skill、产品 API 和已知数据。已有事实足够就直接继续；本文件说明数据准备的决策，不要求重新选择账号或重建环境。

## 判断缺口

先确定 Claim 的最小前置、关联对象及实际消费入口，区分「没有现成样本」「准备方式尚未查清」「已证实无法在授权内准备」。前两者继续查询或准备；字段语义、关联关系或当前值尚未查明时，不能因搜索为空、页面空态或证据不足直接造数。调查、记录和暂停判断按[主文件的问题处理入口](../SKILL.md#验收途中遇到问题)执行。

按验收目标选择准备方式：

- **验证终态展示或配置消费：** 可通过受支持 API 准备符合真实字段语义、关联约束和被测分支的最小状态，再实际观察目标页面。不能无依据地要求完整支付、到期或通知生命周期重放，也不能构造不可能的字段组合、修改被测响应或本地 store 来得到预期画面。
- **验证编辑、状态迁移或外部事件同步：** API 只准备动作之前的状态，实际执行该 UI 动作或对应业务流程并观察结果。直接改成终态不能证明保存、webhook、到期同步等流程正确。
- **两类目标同时存在：** 分别设置 Case、前置与证据，不因展示可以验证就删减流程验收。改变待验状态前保存必要现场证据。

## 数据与 API 查询决策树

接口与业务调查按当前缺口和已有线索选择路径，不规定各来源的必经顺序。业务调查的入口、范围与续验条件按主文件的[业务调查与续验](../SKILL.md#业务调查与续验)执行。未知接口也可从业务对象、时间或线上案例反查，不要求预先知道 endpoint 或 request ID。

| 当前情况 | 查询或行动 | 根据结果继续 |
| --- | --- | --- |
| 缺样本，或不确定现成数据是否满足 | 查询当前授权范围内的对象与关联；T2 按 [T2 测试数据查找与准备](#t2-测试数据查找与准备)优先使用 `redshift` | 合格样本直接复用；没有合适样本或查询不可用时转其它查询或最小准备，不立即向用户索要样本 |
| 有 API 路径、业务关键词或已验证记录线索 | 检索 `~/.config/moego/moe-acceptance/apis/` 的 [已验证参考](api-reference.md) | 适用且充分就使用；未命中或不适用时按剩余缺口选择其他来源 |
| 相关 E2E 有准备代码 | 沿 helper 核对接口、参数与 ID 来源、依赖、作用域、副作用和回读方式 | 信息充分就采用；mock、测试专用入口、固定账号/ID 及整套准备顺序不能直接照搬，不为找请求运行整套 E2E |
| 不知道当前业务走哪个接口或分支 | 查产品调用点与分支条件；仓库归属不明时通过相关 Skill 定位 | 找到实际消费者与接口后只补剩余缺口，不按页面名称猜 endpoint |
| method/path、结构或必填参数不明 | 查对应版本的 proto、OpenAPI 或生成 client；默认值、依赖和副作用查调用方与实现 | 合同明确后执行；影响本次请求的差异未解释时停止该写入，继续补证 |
| 缺真实调用、事件链、状态语义或关联关系，有业务对象、时间或线上案例线索 | 按[业务调查与续验](../SKILL.md#业务调查与续验)使用 `moe-business-context`，从现有业务对象与时间反查请求、事件，再沿字段和关联标识追到源码 | 查明业务链路，再定位目标测试环境可用的准备 API；不以先查完 API 参考或 E2E 为前提 |
| 已改字段但页面不变，或各入口状态不一致 | 从目标页面响应追到字段来源、关联对象、派生逻辑及异步更新机制 | 写入或关联缺失则补前置；数据正确但响应缺字段或映射错误则查接口/协议；响应正确但页面错误则查客户端与版本；确认异步传播才按完成信号有界回读，无进展则调查失败链路 |
| 查询为空、来源失效或该路径无进展 | 核对空结果实际覆盖的范围和失败原因；业务事实仍有缺口时按[业务调查与续验](../SKILL.md#业务调查与续验)选择其它适用来源，通道失效时局部恢复对应通道 | 有新线索则继续；上报条件、尝试记录及独立 Case 续做按主文件的阻塞原则执行 |

业务运行接口不必等于测试准备接口。用日志发现真实链路、状态与关联，再结合当前源码/协议核实目标测试环境受支持的准备 API、依赖及副作用；按前文的展示或流程目标准备，并回读对应消费入口。

`moe-business-context` 可按业务缺口选择 Datadog 日志、源码等证据来源并关联链路；来源已明确时，源码检索直接使用 `github-workflow`，日志查询直接使用 `datadog`，其他来源使用对应专业 Skill。确需库内核对 ID/关系时使用只读查询能力。参数、作用域、副作用和回读方式足以支持下一步时停止扩展查询，不例行再查其他来源，也不把 API 搜索限定在首次登录。

来源不一致时，先对齐操作、版本/分支、环境/Grey 和业务作用域，再补查差异所在层。生成类型说明对应版本的结构；日志只证明该次请求的输入与结果，不能据此推定必填字段、默认值或其它分支。尚未解释的差异影响本次调用时，保留具体缺口，不拼接不同版本的 payload。

日志查询按 `datadog` Skill 使用已知 request ID，或从业务对象、Company/Business、时间与环境逐步收窄。原案例未命中时核对覆盖范围与保留情况，可采用版本、分支和作用域适用的近期同类案例补充机制证据，不冒充原客诉复现。采用前核对 Host 和关联对象；字段可能缺失或截断，空结果可能受索引时延或采样影响，必要时回到 client/schema 或实现补齐。输出仅保留必要的非敏感事实。

例如宠物定制服务在 Legacy/Fulfillment 下可能走不同接口，points 可能由 duration 与 minutesPerPoint 推导。先确认真实分支和语义，再选择最小配置，不能按页面名称猜 `points` 字段或照抄其它环境的 ID。

调查发现不同状态映射或消费入口时，按已确认的业务预期补充范围内的 Case 和断言，不以现有实现代替预期或扩大产品范围。

## T2 测试数据查找与准备

适用于各端及纯接口验收；已有合格数据直接复用。

1. **优先查可复用样本。** 使用 `redshift` 只读查询目标 Company/Business/Location、对象关联与所需状态。连接发现与 metadata 遵循该 Skill 的合同，确认数据源覆盖 T2，不能把默认连接当作 T2。
2. **核对候选数据。** 通过当前产品 API 或目标页面核对业务归属、关联和动作前状态；副本延迟、可见范围或字段缺失影响判断时，以实际消费入口补证。
3. **按缺口转向。** 查询范围已核对但没有合适样本，或 Redshift 不可用于 T2 时，改用其它适用 Skill 或现有产品通道继续查询、最小准备。保留具体缺口，不能把查询不可用写成“没有数据”，也不能切到生产找测试样本。

## 复用合适的请求身份

**优先使用当前已就绪、身份和作用域匹配的环境通道。** 只有 App 验收且已有正确原生环境时，可从 App 内调用产品请求客户端，不为发 API 特意新开 Web；已有 Web 就复用该页面会话。多条通道可用时按业务语义、准备成本和对被测状态的影响选择；现有通道不适用或恢复成本更高时，再补充另一条。

| 当前可用能力 | 如何执行 | 能力边界 |
| --- | --- | --- |
| 已运行的开发 App，且可连接其 JS runtime | 使用当前 App 的产品 `http.open` / `http.rpc` 等既有客户端；iOS 细节见 [App 内请求](ios-runtime-api.md) | 原生身份与环境保留在 App 中；宿主 HTTP 或 Maestro HTTP 不继承它。按 Claim 判断是否允许调用会改本地 store 的 action |
| 合适的 Web 登录上下文 | 在同一 namespace/session 中，通过 `agent-browser eval --stdin` 执行页面内同源 `fetch` | Cookie 由浏览器承载；请求所需的租户、版本及 CSRF 信息按真实客户端合同补充 |
| 工具原生支持与浏览器共享身份的请求接口 | 复用其公开接口，例如 Playwright 的 `BrowserContext.request` | 属于工具管理的 HTTP 请求，不等同页面网络过程；不能将它放进页面 `eval` 或假设 agent-browser 已提供此能力 |
| 专业 Skill 或产品支持独立认证的 HTTP 能力 | 通过其公开合同执行当前授权动作 | 认证必须适用于目标业务；MIS 管理身份不等于商家业务身份 |

具体请求需要匹配实际 Host、环境/Grey、账号、Company/Business 和接口作用域。浏览器同源 Cookie 不会自动补齐前端拦截器；当前商家客户端从页面 query 的 `~c`/`~b` 生成同名租户 headers，并用 `X-Moe-Version`/`X-Moe-Build-Time` 承载版本信息。复用这些事实时保留当前页面的真实值，未知值先查调用点或自然请求，不硬编码测试 ID，也不假设页面模块可从 `window` 调用。

OBC 的 booking identifier/Customer 与商家配置身份分别核对，切 Host 不等于切身份。跨端准备按实际写入主体选择已有受支持能力，消费验收继续使用目标端身份。平台路由或身份细节有缺口时才读对应 reference，不为发请求重建健康环境。

不导出 Cookie、提取原生 token 或建立新的 HTTP session 管理器来拼接认证。认证或接口能力不明确时继续查证，现有受支持能力仍无法满足时说明缺口。请求使用当前工具的实际公开参数；输出仅保留必要事实，工具返回的 `origin`/URL 等附带字段也须避开认证参数。

## 最小准备、回读与续验

先查询可复用数据，只补当前目标缺少的前置。写入前明确对象、环境和授权范围；已有授权覆盖的动作直接执行。共享配置、传播到已有预约等副作用要纳入范围判断，不能靠猜测参数默认值规避影响。按对象合同复用稳定引用、命名或幂等能力，避免重复创建。

检查 HTTP 状态、业务错误及实际目标结果，并在页面或接口回读所需字段和关联。HTTP 200、工具退出成功或公司级响应本身，不能证明全部业务范围和消费者都正确。请求超时或结果含糊时，先查询写入是否发生；仍不能确定就保留缺口，不盲目重写。身份失效只恢复受影响上下文，再确认当前动作前置。

在现有上下文保留 API 操作、来源与版本、参数关系和适用范围，以及必要的数据引用、写前/写后状态、回读依据、保留决定、后续消费入口与待观察结果。版本、Grey 或接口形状变化时，只复核受影响事实。跨任务可参考源码入口与参数关系，具体身份和业务 ID 按新任务上下文取得。

实际 API 业务结果核对后，按 [本地 API 参考](api-reference.md#何时写入及如何更新) 保存或更新对应调用组合；只沉淀已验证范围，保留其他有效组合。存储失败不改变业务结论，也不触发请求重放。

默认保留业务数据；后续 case 需要不同前置时按需选择或调整。约定恢复时执行并核对实际结果，恢复未完成就明确说明。

准备结果只说明前置是否到位。同一 AI 继续目标动作与观察，按 Claim 判断业务结论；API 回读成功不能代替 OBC、预约页面或原生应用实际消费配置的证据。
