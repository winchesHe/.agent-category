# Figma UI 走查

本次改动影响 UI 且有对应 Figma 时，自动进入此分支；只核对已确认范围内的页面、组件和状态。不要求先生成报告或重建健康现场。用户明确只整理材料、禁止修改或暂停时，遵从当前授权边界。

## 先确定设计预期

通过当前可用的 Figma 能力或浏览器读取实际节点、原图及受影响属性，保留节点链接和可确认的版本/读取时间。不能用 Jira 缩略图、实现代码或重画图片代替设计依据。先从设计建立检查点，再检查实现，避免把现状当成预期。只覆盖本期受影响内容，不把整屏旧功能纳入整改。

| 检查内容 | 判定依据 |
| --- | --- |
| 内容与层级 | 组件及内部内容完整，文字、数量、显隐符合对应状态。地图需核对服务区域边界、区域名称和客户位置；只有底图或容器不算完成。 |
| 颜色 | 固定颜色核对设计 token/色值、透明度及状态；动态业务色核对真实配置到元素的映射。不能强求测试数据与 Figma 样例同色，也不能以“颜色来自数据”跳过检查。 |
| 字体 | 核对字体、字号、字重、行高，以及本期相关的换行、截断和文字颜色。 |
| 图标与素材 | 使用对应素材，核对轮廓、填充/描边、尺寸与颜色。语义相近的图标不能替代外观一致。 |
| 布局 | 核对尺寸、间距、内边距、对齐、圆角和边界，确认无遮挡、裁切、溢出。 |
| 状态与交互 | 覆盖本期相关的默认、展开、关闭、选中、禁用等状态；交互结果必须实际操作。 |

对受影响的关键数值属性读取设计值与实际生效值，例如文字字号/字重、图标尺寸、固定色及透明度；记录值和来源，不只写“看起来一致”。浏览器可读 computed style，App 可核对当前构建生效的样式与运行画面；代码声明不能单独证明实际效果。颜色有疑点时核对色彩空间、透明度叠加和背景，不能直接用抗锯齿边缘像素定色。可访问性问题与设计还原分别说明，不能借此自行改色或扩大全量审计范围。

## 按业务场景执行，随状态走查

1. 按页面、状态及平台形成 UI Case。需要独立修复或判定的平台拆成独立 Case，否则在一个 Case 下分别配对。复用健康现场、已确认身份和数据，确认实际代码来源。
2. 执行产品动作并观察功能结果，随即对照当前状态的 UI，在切换状态前截图。例如先核对详情中的标签与小地图，再展开检查大地图，最后关闭确认恢复。不要先跑完全部功能再凭记忆补 UI；明显妨碍操作的 UI 问题先修。
3. 两侧对应同一业务状态和展示区域。保留原图，按相同逻辑比例查看，必要时附带来源的局部放大；不拉伸、重画或裁掉差异。记录设备/图像尺寸，区分设备像素与逻辑尺寸，不给 Figma 原型补造浏览器 viewport。测试姓名、地图底图可不同，但不能掩盖受影响内容、结构或样式差异。
4. 每个检查点写明“对象/状态及设计预期与来源 → 实际值/画面观察及对应图片 → 差异与结论”。按具体配对登记，不能用一句“整体一致”覆盖多个平台和状态。功能与 UI 分别判定，可共享同一次操作现场；最终结论必须对同一实际代码版本成立。

不采用统一像素差分百分比或主观“基本一致”作为通过标准。P1/P2 只决定处理优先级，P2 不自动豁免。可接受偏差必须有产品/设计的明确确认和适用范围，Agent 不能自行放行。

## 修复、复验与停止

发现差异后，在需求和授权范围内按 [repair-and-retest](repair-and-retest.md) 修改，确认 HMR/Fast Refresh 或必要构建已生效，再执行受影响动作、截图并对比；涉及点击区域、显隐或布局事件时，同时复验相关功能。保留不受影响的有效结论，不全量重跑。正常交付应为修复后通过；修复中的“仍有差异”是过程观察，不是把 Case 交回用户的理由。

- 同一 UI Case 以一次完整的“相关修改 → 确认生效 → 实际复验”为一轮。首次走查、保存文件、刷新或纯报告更新不计轮数。第 1～3 轮未通过时继续有依据的修复；第 4 轮仍不符合（超过 3 轮）则停止该 Case 的自动修改，以“不通过”交付残留差异、各轮方案和结果。独立 Case 继续。
- 计数属于同一 Case 的修复过程，不等于报告轮次；不得通过换 Case ID、换修复方法或换对话清零。目标或设计标准真实变化时记录新依据再重新界定复验范围。
- 必要权限、标准、用户决定或运行前置确实缺失时，按主文件的问题处理入口调查和暂停，不为凑满四轮盲改。用户主动停止时如实记录已观察差异与停止原因，不宣称达到修复上限。
- “信息不足”只用于无法可靠判定：例如适用读取路径均无法取得 Figma、互相冲突的版本无法确定当前预期，或必要状态经过有依据的恢复仍不可观察。说明已尝试路径、结果及最小继续条件。还没读取、没截图、不知道怎么改、一次加载失败都不是最终交付理由；明确看出不符则记录差异并继续修复。
- 已完成对比但交付图片遗失，属于证据缺口，不能把既有业务结论改成信息不足。按授权补证；证据未齐备不宣称整体交付完成。

## 证据与报告

UI Case 和功能 Case 分别判定，功能通过不能覆盖 UI 差异。修复后重新采集受影响的实现图，仍有效的设计图可复用；保留真实采集时间。旧图须复核仍代表当前状态才能采用，不能自动继承通过；更换图片或出现相矛盾的画面时重新核对受影响检查点。仅获授权整理报告时，说明矛盾与交付缺口，不擅自启动业务修改或补验。

需要报告时复用 `cases`、`ui_acceptance`、资产与轮次 API；按 [UI 走查数据与呈现](report-publishing.md#ui-走查数据与呈现) 标记 `kind="ui"` 并显式配对。HTML 和 Site 提供独立「UI 走查」栏目：左为 Figma，右为实现，窄屏依次上下排列并标注角色，原图可放大；每组图片下面展示对应检查点的预期、实际观察与结论。当前栏目采用当前有效证据，旧图和失败过程保留在历史；未解决差异直接写入当前观察，不能用 Case 总结或其他配对的通过覆盖。

报告工具只检查结构、引用与显式结论矛盾，不判断视觉是否一致。不能用两张图已配对、导出成功或自动图片差分替代对实际画面和属性的检查；没有报告需求也必须完成触发条件成立的 UI 走查。

维护此 Skill 时，用不提前指出缺陷的设计/实现输入验证能否发现偏差，并配无偏差与动态颜色正确的对照。模板测试只证明数据与呈现合同；未执行独立行为评测时如实说明，不能据此宣称 Agent 已能可靠识别视觉差异。
