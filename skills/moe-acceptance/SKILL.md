# MoeGo 本地验收

由同一 AI 在连续 session 中完成准备、验收、调查修复和交付。本文件是 core：保持任务目标与已确认事实，选择下一步并判断完成条件；references 承载各模块的具体做法。模块可按当前请求单独使用，共享当前会话，不拆成用户交接或独立运行角色。

## Core 的职责

1. **保持任务约定。** 从当前对话和已确认材料提取范围、预期依据、授权边界与交付要求。组织动态 Case 和断言；代码现状用于理解和定位，不能单独作为预期标准。标准足够就直接执行，关键歧义才提出短提案集中对齐。
2. **选择下一步。** 根据当前 Case 及实际缺口，进入相应模块；复用已成立的前提和结果。模块结束后核对其产出是否满足当前目标，再决定继续、补前置、调查、复验或汇总，不把模块顺序当作每次必跑的流水线。
3. **维护连续性与完成判断。** 在[连续上下文](#连续上下文)中保留事实、适用范围、问题和下一步。发生变化时判断哪些输入、观察或证据失效，从最早失效步骤接续；分别判断业务结果、证据充分性和约定交付物，统一按[继续、暂停与结束](#继续暂停与结束)选择后续动作，再按[并发与资源](#并发与资源)处理资源。

AI 负责账号与数据选择、Case 顺序、故障归因、修复范围和结论。工具提供事实与确定动作；直接复用现有浏览器、项目 API 和专业 Skill，不新增总控 CLI、case adapter、动作宏或业务状态机。参数、schema、业务 ID 或工具能力不明时先探索，不能猜测。

## 验收主流程

完整验收围绕当前 Case 推进：明确目标与 Case → 补齐前置 → 执行并采证；发现问题后局部处理、回到受影响步骤复验；最后汇总交付。已有标准或健康现场时，按[场景决策树](#场景决策树)直接进入当前需要的一步；只准备环境、只采证或只整理报告时，以本次约定范围为止。

1. **明确本次要验什么、交付什么。** 从当前对话和已确认需求确定范围、预期依据、是否包含修复、必要证据与交付形式，沿用已有约定。只有影响对错或交付的关键歧义才集中对齐；标准足以判断后准备 Case。参考 [标准提取与复用](references/case-execution.md#复用标准与直接执行)，完成条件按[继续、暂停与结束](#继续暂停与结束)。
2. **准备可执行、可判断的 Case。** 为当前场景写清 Claim、前置条件、动作、预期断言及举证方式；条件或动作不同且需要独立结论的场景分别记录，一个 Case 可含多个断言。标准明确且知道如何观察结果后进入准备；Case 随发现增补，不降低标准、不冻结整套清单，扩大范围或改变预期才重新对齐。参考 [Case 设计](references/case-execution.md#复用标准与直接执行)与[证据选择](references/evidence-capture.md#证据档位)。
3. **补齐当前 Case 的前置。** 按缺口使用[环境准备](references/environment.md)、[账号与资格](references/account.md)、[数据与配置](references/data.md)，已有有效结果直接复用，三者不互设固定先后。只准备动作所需条件，不能提前完成待验 UI 动作；确认实际版本、身份和数据满足当前 Case 后开始执行。
4. **实际执行、观察并及时留证。** 在目标入口执行 Case，按[观察与结论](references/case-execution.md#观察与结论)判断有效结果；改变现场前按[采证规则](references/evidence-capture.md)保存并查看必要证据，逐项关联断言、实际观察和结论。有对应 Figma 的 UI 改动同时按 [UI 走查](references/ui-design-review.md)核对。当前 Case 的观察与必要现场证据核对后继续下一项；出现缺口或差异进入下一步，独立 Case 可继续。
5. **记录问题并局部复验。** 按[问题处理入口](#验收途中遇到问题)结合授权选择收集问题、调查、恢复或修复，保留问题所属 Case、现象、证据及下一步；具体操作见 [repair-and-retest](references/repair-and-retest.md)。修复或热更新生效后，只补失效前置并重验受影响断言，回到第 3 或第 4 步；仍需等待时保留现场和接续位置。恢复成功、已记录问题或已生成阶段报告都不能代替复验。
6. **汇总、核对并交付。** 对照约定范围检查已执行、未决与未覆盖内容，分别判断业务结果、证据充分性和交付物。按需使用 [report-publishing](references/report-publishing.md)整理报告，并按 [Case 与截图一致性检查](references/evidence-capture.md#case-与截图一致性检查)核对最终图文；缺口返回对应步骤。按[继续、暂停与结束](#继续暂停与结束)决定后续动作，再按[结果输出](#结果输出)交付结论或进展、剩余缺口及实际资源处理状态。

## 模块职责与产出

进入模块时只补当前目标缺少的输入；已有事实直接复用。处理后说明实际结果、必要依据、仍有的缺口，以及影响后续动作的变化或副作用；记录沿用当前会话和 Case，不要求交接文件或另建状态表。有缺口的产出用于决定下一步，不能视为目标已满足；局部完成也不能代替后续业务判断或整个任务完成。

| 模块与按需入口 | 负责什么 | 用于继续判断的产出 |
| --- | --- | --- |
| 上下文分析与 Case 设计：[case-execution](references/case-execution.md) | 将已确认需求转成场景、可观察断言和必要证据；随发现补充覆盖 | 范围与预期有依据，当前 Case 的前提、动作和判断方式明确；未决歧义已定位 |
| 账号与资格：[account](references/account.md) | 首次选择账号时按当前请求和默认配置取得候选，核对业务范围与功能资格，按平台准备或恢复登录 | 实际身份与目标一致，当前 Case 所需资格成立；不以账号候选或登录工具成功替代核验 |
| 环境准备与恢复：[environment](references/environment.md) | 准备或复用服务、路由、浏览器或设备，确认实际消费的版本与资源归属 | 当前动作所需入口和依赖适用；缺口已定位到受影响组件 |
| 数据与配置：[data](references/data.md)、[API 知识](references/api-reference.md) | 查询、选择并最小化准备对象、关联及配置，核对实际消费结果；按需检索和维护已验证接口知识 | 当前 Case 的输入成立，写入与约定恢复责任清楚；准备没有代做待验业务动作 |
| Case 执行与现场证据：[case-execution](references/case-execution.md)、[evidence-capture](references/evidence-capture.md) | 实际操作、观察、及时采证并逐项判断；提供 Case 与截图一致性的检查标准 | 观察覆盖哪些断言、结论和限制明确；必要现场证据已保存并检查，缺口已记录 |
| UI 设计走查：[ui-design-review](references/ui-design-review.md) | UI 改动有对应 Figma 时建立设计预期，核对实现并在授权内修复复验 | 对应平台与状态的设计、实现及检查点可关联；UI 结论与功能结论分别成立 |
| 问题调查、修复与复验准备：[repair-and-retest](references/repair-and-retest.md) | 获取能区分原因的事实，恢复受影响组件或修复范围内差异，确认实际生效 | 原因或剩余缺口、实际变化、受影响断言和复验起点清楚；生效后回到原 Case 验证 |
| 报告整理：[report-publishing](references/report-publishing.md) | 消费已有结论和证据，组织最终图集；按一致性标准逐 Case 核对最终页面后交付 | 截图、Case 描述、结论及限制可对应；生成成功不代替图文核对、业务通过或证据充分 |

## 编排规则

### 场景决策树

先遵循本次请求的范围，再按当前事实选择下一步；不要求从上下文分析重新开始，也不把下表当作必跑清单。多个场景同时命中时，先保留即将消失的必要证据，再补当前动作依赖的缺口；已有事实仍适用就复用。

| 当前场景 | 下一步与按需入口 | 处理后从哪里接续 |
| --- | --- | --- |
| 已有标准和健康现场续验 | 直接执行当前 Case 的下一个必要动作；不重复确认、不重跑登录桥接或全量 preflight，简单续跑只需本文件和已有上下文 | 继续当前 Case 的动作、观察与留证 |
| 新验收、范围变化，或业务标准缺失、有关键歧义 | 从当前对话和已确认需求提取范围、可观察预期、必要证据与交付物，按 [Case 设计](references/case-execution.md#复用标准与直接执行)形成当前场景；业务依据需要补证时按[业务调查与续验](#业务调查与续验)处理，仍有影响判断的歧义时提出短提案集中对齐 | 标准足够后执行相关业务动作；未决歧义只阻塞依赖它的动作，不阻塞独立准备或已有报告整理 |
| 只准备环境、身份或数据 | 进入对应模块，完成本次约定的准备范围 | 返回准备结果与剩余缺口，不自动扩大为业务验收 |
| 只采证或整理已有材料 | 沿用已有场景与观察，按 [证据](references/evidence-capture.md)或[报告](references/report-publishing.md)处理；只采证不要求报告 API | 交付本次约定材料并注明缺口；只整理报告不启动业务复验 |
| 首次准备环境，或目标版本、后端依赖、路由及设备/应用状态有缺口或变化 | 按[环境准备与恢复](references/environment.md)选择对应入口，只准备或恢复受影响部分 | 确认当前动作所需前置和实际消费版本后，回到依赖它的 Case |
| 首次选择账号，或 Company/Business/Location、功能资格或登录有缺口 | 按 [account](references/account.md)选择、核验或恢复身份；已有合格身份直接复用，不要求先完成数据探索 | 恢复必要业务输入后继续原动作，不重建无关环境或数据 |
| 缺少合格测试样本、准备方式未明、关联字段不清，或已改数据与页面状态不一致 | 按 [data 的决策树](references/data.md#数据与-api-查询决策树)查找可复用数据、调查真实字段与消费入口，再补最小前置，不提前完成待验 UI 动作 | 前置满足后回到目标端执行原 Case；发现接口、客户端或版本差异时转问题处理 |
| 需要查询、保存或修订本地已验证 API 知识 | 按 [api-reference](references/api-reference.md)检索并核对适用条件；只有源码线索时不登记为真实调用通过 | 查询结果用于当前数据准备或业务动作；知识保存失败不改变已有业务结论，也不为补记录重发请求 |
| 确实需要第二个浏览器上下文，且账号/环境独立、数据互不干扰并有收益 | 按 [parallel-browser](references/parallel-browser.md)建立必要隔离，并遵守[并发与资源](#并发与资源) | 各自继续对应 Case，共享编辑和服务重启串行；单侧故障只恢复受影响侧 |
| 需要定位准备耗时、失败组件或重试原因 | 按 [observability](references/observability.md)读取已有日志及实际计时，不为补日志重跑准备 | 带上新事实回到当前准备或问题调查；日志不代替业务观察 |
| 本次 UI 改动有对应 Figma | 按 [UI 设计走查](references/ui-design-review.md)读取设计原图与属性，增加独立 UI Case；业务动作后随即核对画面、采证并逐项记录 | 无需报告也执行；差异在授权内修复并热更复验，超过 3 轮仍不符才停止该 Case 的自动修改；判定依据不足先调查，独立 Case 继续 |
| 验收途中出现异常、业务差异或前置未就绪 | 按[问题处理入口](#验收途中遇到问题)选择调查、局部恢复、修复、等待或暂停；只读取当前缺口的具体做法 | 从最早失效步骤继续原 Case；恢复成功后仍需验证受影响断言 |
| 修改、刷新、关闭或清理将使必要证据消失 | 先按 [evidence-capture](references/evidence-capture.md)保存并检查 before、瞬时错误或过程证据；报告可以后置，现场不能补造 | 留证后继续原定动作；缺失现场如实记录，不假装已采集 |
| 需要正式材料，或已有报告的截图、描述及呈现有缺口 | 用已有结论与资产按 [report-publishing](references/report-publishing.md)生成或更新材料，并核对最终页面的 Case 与截图一致性 | 错图或渲染错误只修报告；原始证据不足按授权局部补验或保留缺口。核对完成后按约定交付；无报告需求时输出可判定摘要，不自动生成 HTML/Site |
| 准备收尾，或用户要求暂停、结束或调整范围 | 按[继续、暂停与结束](#继续暂停与结束)核对剩余约定和当前可执行动作 | 按判断继续、暂停受影响部分或结束，再处理资源与结果输出 |

### 连续上下文

`AcceptanceSession` 是当前会话的工作记忆，由同一 AI 在推进时维护，默认记录在当前对话中可回读的验收进展与接续摘要里；已有任务记录直接复用。Case、证据和报告沿用各自已有产物，上下文保存其引用，不复制内容，也不要求额外创建状态文件、session manager、全局 ready 状态、TTL 或工具流水线。

| 保留什么 | 用来决定什么 |
| --- | --- |
| 任务约定：范围、预期依据、授权和交付要求 | 哪些动作属于当前任务，什么条件下可以结束 |
| 已确认事实及依据：worktree/实际版本、服务与路由、浏览器或设备、身份、数据配置、Case 观察与证据、资源归属 | 哪些前提和结果仍可复用，分别适用于哪些场景；设备 UDID/serial、build/JS 来源等只在实际需要时保留 |
| 当前进展：正在处理的 Case、具体缺口、已尝试路径及结果、待复验内容、下一步 | 从哪里接续，哪些部分受阻，哪些独立 Case 仍可继续 |

关键准备完成、Case 观察或问题发生变化、暂停及恢复时，更新简短记录，保留当前约定、仍有效的事实与引用、未决事项和下一步，不为每次工具调用重新登记。模块切换不丢弃上下文，缺参数就只补该参数；普通 HMR、刷新或 Case 结束不触发全量核验。

变化按影响范围处理：配置改变后更新适用条件，不抹掉原条件下的历史观察；代码变化后确认实际生效并复验受影响断言，不自动重建账号和数据；身份恢复后补回被恢复动作清掉的必要输入，再执行原业务动作。事实是否仍适用影响下一步，不用单一的“当前阶段”替代判断。

### 验收途中遇到问题

先确认受影响的 Case、预期与实际现象；在刷新、修改或关闭可能消除现场前保存必要证据。保留已有有效结论，账号/环境变化或失败信号只触发相关检查，不触发全量重建。是否继续、暂停或收尾统一按[继续、暂停与结束](#继续暂停与结束)判断。

#### 选择下一步

按已有事实选择最小有效动作；异常现象不等于已证实无法继续，也不要求先走完全部分支。

| 当前事实 | 行动与按需入口 |
| --- | --- |
| 原因已明确，当前授权足以处理 | 直接恢复受影响组件或修复需求内差异；环境、账号、数据按对应 reference，代码更新与来源确认按 [repair-and-retest](references/repair-and-retest.md)。随后回到原 Case |
| 原因未明，仍有能区分原因的检查 | 选择能改变判断的调查动作，并根据结果调整候选原因；具体方法按 [调查动作与记录](references/repair-and-retest.md#调查动作与记录)。通用错误页、一次空查询或没有现成样本都不足以排除剩余路径 |
| 当前 Case 的业务预期、字段语义、状态关系或事件链路存在缺口 | 按[业务调查与续验](#业务调查与续验)补齐影响下一步判断的事实 |
| 所需构建、部署或异步前置正在执行 | 核对真实对象及完成信号，涉及版本时确认目标版本，在当前运行支持时有界等待；前置成立后继续。细节按 [等待构建或部署后续验](references/repair-and-retest.md#等待构建或部署后续验) |
| 已证实缺少必要权限、标准或用户决定，或当前没有可执行的适用路径 | 按[继续、暂停与结束](#继续暂停与结束)处理受影响部分；能力未知或尚未查询不等于能力不可用 |
| 业务观察已有依据，仅证据或报告交付有缺口 | 有效媒体未采用或渲染失败按 [report-publishing](references/report-publishing.md) 修复呈现；原始证据缺失则在授权范围补验受影响 Case，保留新的采集时间。用户仅要求整理材料时不自行扩大为业务执行 |

#### 业务调查与续验

当前 Case 的业务预期、字段语义、状态关系或事件链路存在缺口时，使用 `moe-business-context` 定向调查。沿用当前目标、已知事实与已尝试结果，只补影响下一步判断的信息；已有明确来源时直接使用对应专业 Skill。环境、账号和请求通道问题沿对应验收模块处理。

事实足以支持当前 Case 的准备、执行或判断后，继续原验收流程，不因调查完成而结束任务。实现事实与预期依据分别核对；两者冲突时保留差异，不能用当前实现改写验收标准。

#### 调查记录与复验依据

在已有任务记录或会话中及时保留「缺口 → 路径及依据 → 实际动作与结果/证据 → 下一步或排除原因」。记录以能支持下一步判断和恢复为准，不强制新建文件或填满固定表格；未执行的建议不计为尝试。

重复动作无新增证据或达到该路径的等待/重试上限时停止重复，转向有依据的其它路径，不机械穷举所有工具或原因。记录实际变化、失效前置和受影响断言；复验范围按 [repair-and-retest](references/repair-and-retest.md#恢复后的复验范围)，业务三态与具体动作语义按 [case-execution](references/case-execution.md#观察与结论)。

### 继续、暂停与结束

模块返回结果、阻塞条件变化或用户调整任务约定时，由 core 按下面规则选择下一步；准备收尾或清理前核对完成条件。Case 的「通过／不通过／信息不足」描述业务观察，不直接决定整个任务是否结束。

**继续：** 仍有本次约定内已授权、可执行的必要动作，或可能改变判断的调查路径时继续，不等待用户再次催促。阶段报告不能替代调查或复验；构建或部署仍在执行且当前运行能够继续等待时，按[等待构建或部署后续验](references/repair-and-retest.md#等待构建或部署后续验)有界等待，条件成立后接续，不能仅回复“等待部署”就结束工作。

**暂停受影响部分：** 须有具体依据：必要权限或用户决定缺失；剩余适用路径已失败或有依据排除且无新线索；或外部前置未完成且当前运行无法继续等待。说明已完成项、受影响 Case、已尝试动作及结果、剩余路径不可执行的原因、最小继续条件与恢复后动作，更新[连续上下文](#连续上下文)。独立可做的 Case 继续，现场按资源边界保留；不把尚可自行处理的问题交回用户。用户明确暂停或缩小范围时遵从，并区分主动停止与路径已穷尽。

**恢复后接续：** 继续条件成立后，确认身份、数据和实际代码来源中受影响的前置，从最早失效步骤继续原 Case；必要时先重建动作输入，再实际操作、观察并留证。恢复成功不等于业务验收通过。

**正常结束：** 本次范围来自用户请求及已有会话约定，须同时满足以下条件，由 AI 根据事实判断，不例行再问一次“是否结束”：

1. **约定工作已完成。** 完整验收中，该验的 Case 已取得支持结论的观察，范围内要求的调查、修复与复验已做完，没有遗漏的必要动作。只准备环境、只采证或只整理已有材料时，只核对该项约定；材料整理完成并注明已有缺口，不等于完整业务验收完成。
2. **必要证据和交付物已完成。** 约定证据已保存并核对，Case、实际图文与结论一致；需要的报告、发布或摘要已完成交付核对。无报告要求时摘要和约定证据足够，不额外生成报告。
3. **没有待继续的约定。** 当前任务没有尚待执行的 Case、部署后复验或其它已约定动作。用户已说明后面继续时，本轮做完仍保留任务上下文；不得因回复结束或生成阶段报告自行结束任务。

业务结论为“不通过”也可以完成验收任务：例如本次只要求验收并上报缺陷，失败已确认、证据齐备且问题已按约定交付，修复不在本次范围内。若本次还要求修复并复验，则不能在发现失败后当作任务完成。

**用户终止：** 用户明确结束、取消或接受以部分结果收尾时可以终止，但要如实标明未完成项，不能改写为全量验收完成。

必要观察、证据或约定动作尚未完成时，按上面的继续或暂停规则处理；结束范围不明时先保留现场。正常完成或用户终止后，再按[并发与资源](#并发与资源)处理资源，并在[结果输出](#结果输出)中说明实际结果。

### 并发与资源

默认一个浏览器上下文，确有独立账号/环境、数据互不干扰且有收益时才使用第二个，最多两个。每个 session 内 case 串行，共享 worktree 的代码编辑与服务重启串行；真正并行编辑使用独立 worktree。只恢复故障一侧，HMR 后分别判断影响。

浏览器默认 headless，只有用户明确要求显示才使用 head；不在同一 session 内隐式切换模式。Android 默认后台模拟器并按 serial 操作，按需展示与资源恢复见平台 reference。iOS 默认后台原生驱动，不主动显示 Simulator 窗口；用户需要看现场时复用健康设备、App 和 Metro，只补展示，不因此切换驱动或重放准备，也不为转后台关闭已有窗口。多需求保留现场与并行操作分别判断：设备、代码、服务、驱动和业务数据须按需隔离，窗口可见与否不决定并行能力；依赖宿主全局鼠标、键盘或焦点的动作串行。默认保留业务数据，先查后建避免污染；有配额或污染风险时暂停说明。

资源保留或清理由[继续、暂停与结束](#继续暂停与结束)的判断决定。结束收尾只清理登记为本任务创建且不再承担交付或接续用途的资源，并核对实际结果；复用服务、业务数据、诊断日志、正式证据和 Site 保留。准备环境供后续使用时，运行环境本身是交付物，不能因准备任务已完成就将其销毁。清理失败保留收据并单列为未完成项，不用全局关闭或杀进程。

只有登记为本任务创建的开发 worktree 才进入移除：交由创建方的现有收尾流程与授权执行（如 `github-workflow` 的安全 Release），目录内的可重建缓存随目录回收，移除后确认目录与登记均已清理。用户自有或复用的 worktree 一律保留。创建方门禁拒绝（未提交改动、未推送提交、未知 ignored 文件等）或没有可用流程时，保留 worktree 并列为未完成项，不强制删除，也不为通过门禁而提交、stash 或丢弃改动。需要接续现场时保留原 worktree；归档只保存必要修改和证据，不把整个 worktree 或缓存复制到验收目录。长期报告目录独立于开发 worktree，生成产物按 [报告产物收尾](references/report-publishing.md#报告产物收尾) 处理。

## 验收与交付约定

### 验收与证据

分别核对业务结果、证据充分性和约定交付物，不能用其中一项代替其它项：

- **业务结果：** 实际页面/接口观察必须覆盖 Claim。每个 Case 明确为「通过」「不通过」「信息不足」；脚本成功、页面能打开或 HMR 成功不等于业务通过，缺观察不得补写通过。
- **证据充分性：** 已有可靠业务观察、只缺约定媒体时，保留业务结论并说明证据缺口。若画面与结论冲突或关键观察本身未核实，则回到对应断言调查，不能一律解释成缺截图。
- **交付完成：** 业务通过但必要证据或约定报告未完成时，不宣称整体完成。仅整理报告的任务可以完成材料整理并注明缺口，不据此宣称完整业务验收已完成。

执行与采证遵循以下边界：

- HMR **连续性验证**证明新代码可观察且原 page/session、登录态保持。
- **业务修复验证**要求真实相关代码改动及受影响动作、断言的重新执行。无关文案不能证明业务修复；没有真实 bug 不制造业务改动。
- 非视觉结果保留最低充分的输入、观察和结论；结论依赖页面状态时，在改变该状态前保存并目视检查能对应条件、对象和结果的截图，不能用文字碎片或文件存在代替内容判断。时间性 Claim 才增加短媒体，已有有效证据可复用。用户明确排除截图时遵从，但不声称完成视觉验证。
- 每项断言关联实际观察及必要证据；同一图集可支持多个断言，但不能从一个提示推定后续回滚或保存结果。已验证且仍适用的前一 Case 结果可作为后续前提，引用原 Case 与采集事实，不要求独立重拍 before。
- UI 走查与功能验收分别判定；报告用独立栏目展示设计稿与实现截图，复用现有 Case、显式证据和历史轮次，检查点关联到对应平台/状态的图片，不把配图或功能通过当作 UI 通过。
- UI/媒体按 `case_id` 归属；前后对比使用同一 `comparison_id`，viewport、尺寸和覆盖范围必须来自采集事实。

交付前由报告模块按 [Case 与截图一致性检查](references/evidence-capture.md#case-与截图一致性检查)逐 Case 核对**最终采用且实际呈现的证据**，留下图中事实如何支持文字结论的依据，不只记录“已检查”。Core 根据核对结果决定交付、修正报告或在授权内补验受影响断言；存在影响约定举证的缺口或画面冲突时不宣称交付完成。无报告时对交付的摘要和媒体执行同样核对。自动校验不能代替 AI 看图判断，checkpoint 能减少遗漏，不能保证业务理解或结论正确。

报告沿用现有产物合同：

- 新任务的正式证据统一保存在 `~/.config/moego/moe-acceptance/<任务ID>/`，同一任务的 Case 和轮次共用该目录。已有任务继续复用已确认的目录，不因新约定自动迁移；目录结构与调用方式见报告 reference。
- 一个任务固定一个 `report/index.html`，最多一个 Site，更新复用。纯渲染/发布失败只修呈现，不改业务结论、不重跑业务；新采集不能冒充旧现场。
- HTML 与 Sites 生成前均按 [导出诊断与处理](references/report-publishing.md#导出诊断与处理) 检查内容、证据和呈现缺口；两者复用同一份已采用证据与现有模板，不另维护业务结论。报告 API、导出及更新方式由 [report-publishing](references/report-publishing.md) 维护，发布使用 Sites Skill。
- 多次验收的报告使用显式轮次与稳定 Case ID，当前采用的证据按 ID 选择；旧图保留不等于继续展示或自动有效。同一 HTML 默认展示当前轮次，可切换历史快照及其独立图集；历史结论不参与当前汇总。旧报告需显式升级，具体调用和限制按需读报告 reference。

### 结果输出

过程中简要说明当前 case 的观察、判断、动作、代码/HMR 状态和下一步。结束时一次性核对并输出中文摘要：已执行 case 与依据、实际账号/环境/数据前置（无秘密）、代码变更与可确认版本、未决问题、风险和交付状态。已有 runId 可用于关联；没有日志标识不编造。

业务结果、证据充分性和约定交付物按[验收与证据](#验收与证据)的判定分别说明，是否结束按[继续、暂停与结束](#继续暂停与结束)判断。代码交付、清理和报告发布各自列明实际状态；仓库检查结果与业务观察分开呈现。
