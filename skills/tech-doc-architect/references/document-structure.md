# 文档拓扑与内容模型

## 先决定单页还是文档集

满足以下任一条件时优先拆成 Overview + 专题：

- 至少有三个独立且复杂的机制问题。
- 状态、失败或恢复需要单独的图和解释。
- 读者既包括快速评审者，也包括需要追实现的工程师。
- 单页正文必须频繁跳转抽象层级才能讲清楚。

单一组件、短协议或局部流程若能在一屏到数屏内讲清楚，保持单页，避免为了“体系感”制造空专题。

## 沿阅读主线组织专题

确定文档集后，在写正文前列出每页的问题、依赖的前文结论和后续入口。优先沿读者理解系统所需的因果链路排列，例如“输入如何形成 → 前置如何准备 → 动作怎样执行 → 结果如何判断 → 如何交付与恢复”；这只是示例，实际主线由系统机制决定，不固定章数。

- 前一页提供下一页需要的概念或结果，避免按源码目录排列后让读者自行拼接链路。
- 平台或实现差异作为主线对应节点的下级专题；父页说明共同机制与分支选择，子页解释差异，再链接回共同主线。独立问题不强行嵌套。
- 重构时重新检查问题边界和依赖，不能只把原有章节分别搬到子页。
- 可以复用一个贯穿示例，逐页解释它在当前环节的变化；示例与真实运行证据明确区分，不在每页重复完整背景。

## Overview 合同

Overview 负责建立地图，不负责展开全部机制。通常包含：

1. 标题、副标题和一句话结论。
2. 系统上下文图与边界规则。
3. 内部职责图或职责表。
4. 核心运行模型的短摘要。
5. 关键不变量。
6. 专题导航。
7. 必要时补充部署边界。

Overview 的成功标准是：领导或新成员读完后能复述系统边界和核心所有权，并知道深入问题应该去哪一页。

## 专题页合同

每个专题用一个问题命名，在开头用一句 callout 或摘要给出答案。开头简短说明承接前文的哪项结果，以及本页进一步解决的问题；让从链接直接进入的读者也能定位自己。随后只展开对该问题必要的内容：

- 一张主图。
- 核心概念或阶段。
- 正常路径。
- 与该问题直接相关的失败、恢复或降级语义。
- 验证证据。
- 精选代码入口。

页尾提供有明确阅读目的的继续入口，以及返回 Overview 的路径。主线页按需要链接上一篇、下一篇；分支页链接回父专题与共同后续节点，不制造不存在的前后顺序。

常见问题族包括请求执行、状态与持久化、能力装配、交付与展示、部署与验证。它们是候选，不是固定五章。

## 平台无关内容模型

写作前在工作记忆或临时草稿中维护以下字段：

```yaml
document:
  title: ""
  one_sentence: ""
  audience: []
  reader_questions: []
  scope:
    in: []
    out: []
  evidence: []
  vocabulary: []
  overview:
    context: ""
    internal_model: ""
    invariants: []
  topics:
    - question: ""
      answer: ""
      diagram: ""
      concepts: []
      normal_path: []
      failures: []
      recovery: []
      verification: []
      code_entries: []
```

这不是要求用户填写的表单，也不一定要生成文件；它用于保证不同输出载体共享同一事实和术语。

## 图表与正文的分工

| 内容 | 首选表达 |
|---|---|
| 参与者、系统边界、外部依赖 | C4 / 系统上下文图 |
| 组件职责、所有权、依赖方向 | 容器图 / 分层架构图 |
| 请求、事件、中断、恢复顺序 | Sequence / Swimlane |
| 状态、权威记录、终态 | 状态模型 / 数据生命周期图 |
| 阶段门禁、加载与投影 | Pipeline |
| 精确责任、状态或来源映射 | 表格 |
| 设计理由、例外和失败语义 | 简洁正文 |
| 实现追溯 | 精选代码入口表 |

一张图只回答一个问题。若标题无法写成明确问题，通常说明图的范围还没有收敛。
