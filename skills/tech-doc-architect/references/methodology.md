# 技术架构文档方法论

## 核心判断

专业技术文档不是章节模板，而是一条编译链：

```text
代码 / 配置 / 测试 / 运行证据
              ↓
        技术事实模型
              ↓
      文档拓扑与图表计划
              ↓
  Feishu / Obsidian / Markdown
```

载体改变时只替换最后一层。事实模型和文档语义保持不变，避免三种输出长期漂移。

## 事实模型

按任务需要从证据中提取以下信息块，而不是机械生成同名章节：

| 信息块 | 需要回答的问题 |
|---|---|
| 目的与读者 | 为什么需要这份文档，谁要用它做什么判断？ |
| 系统上下文 | 谁使用系统，系统与哪些外部对象交互？ |
| 边界与所有权 | 什么属于系统，谁拥有状态、顺序和恢复责任？ |
| 逻辑职责 | 哪些组件以什么稳定契约协作？ |
| 生命周期 | 一次请求、事件、任务或数据如何开始、变化和结束？ |
| 状态权威 | 哪些记录回答“当前状态”和“历史发生了什么”？ |
| 不变量 | 即使失败、取消或重启也必须保持什么？ |
| 失败与恢复 | 失败在哪里被隔离，如何诊断，如何收敛？ |
| 验证证据 | 哪些测试、观测或运行产物能够证明不变量？ |
| 代码入口 | 读者从哪里进入实现，而不需要遍历文件树？ |

只把有直接证据的信息写成确定结论。命名和现有文档是线索；代码路径、schema、测试断言和运行结果通常是更强证据。关键事实发生冲突时，先解决冲突或显式标注，不能靠更流畅的文字掩盖。

## 由浅入深的认知顺序

默认顺序是：

1. 一句话定义系统及其价值。
2. 系统上下文与外部边界。
3. 内部职责和主要所有权。
4. 核心请求或事件生命周期。
5. 状态模型、能力装配、交付等专题。
6. 失败、恢复、部署和验证。
7. 有选择的代码入口。

这是认知顺序，不是强制目录。如果读者只关心库或协议，可以从契约与使用路径开始；如果文档用于事故排查，可以把故障域与状态权威提前。

## 一节内容的表达语法

一个成熟章节通常只需要四种材料：

1. **结论句**：先说本节要建立的判断。
2. **图或表**：表达关系、顺序、状态或精确映射。
3. **约束解释**：说明为什么这样设计、边界在哪里。
4. **失败与证据**：说明异常时如何表现，以及如何验证。

不要让每节都套齐四项。若一张表足够，就不要再写三段同义文字；若正文只是在朗读图，应该删除或改写为设计理由。

## “专业”的六个可观察维度

- **事实正确**：结论来自当前实现与证据。
- **抽象一致**：一张图和一个章节保持同一抽象层级。
- **边界清楚**：内部/外部、控制/执行、状态/展示等关系可辨。
- **演进可解释**：生命周期、不变量、失败与恢复闭环。
- **可追溯**：关键结论能落到 schema、测试、记录或代码入口。
- **可阅读**：Overview 足够短，复杂性被拆到专题而不是隐藏。

## 三种工作模式

### 新建

先建立事实模型和 Overview，再选择一个最能暴露架构边界的专题作为代表性样板。样板通过后复用术语、结构与图表语言。

### 重构

先把现有内容拆成“有效事实、过期结论、重复表达、历史过程、缺失主题”。有效事实迁移到新拓扑；过期与过程性内容直接删除，不建立“旧版说明”章节拖累正文。

### 更新

从变化事实反向定位受影响的图、表、章节、专题链接和验证说明。结论变化时直接改写原段落；只有仍具决策价值的历史才进入 ADR 或附录。
