# 联调失败与运行结果排查

- ID：`MDEV-DEBUGGING`
- 适用：请求失败、字段缺失、前端显示异常，或环境、服务版本与业务结果不一致。

## 从真实请求确定失败层

先保留原问题的对象、身份、时间窗口和预期结果，再查看实际 host、path/完整 RPC 方法、参数、响应及可用的 request/trace ID。端口、域名、环境和服务名从当前客户端配置、部署与请求记录核对，不套历史域名表。

| 当前证据 | 下一步 |
|---|---|
| 请求未发出 | 查页面条件、校验、事件与请求入口；前端方法见[前端开发](frontend-dev-flow.md) |
| 请求到了错误环境或版本 | 对照运行配置、实际路由和目标镜像；不要用分支名或页面显示标签代替证据 |
| 响应已有字段，页面仍缺失 | 沿解析、转换、缓存/状态与渲染追到丢失位置，不直接要求后端或 SDK 重发 |
| 响应缺字段或接口报错 | 从准确请求和调用代码定位入口，再沿同一请求的下游输入与输出核对 |
| 入口成功，异步结果未完成 | 查接收、调度、发送、消费与持久化；成功受理不是业务终态 |

协议类型帮助解释报文，不足以确定仓库。Java api-v3、client-api、Node BFF、legacy HTTP 和 Go RPC 都可能是入口；只保留实际调用中存在的层。

## 选择对应证据

| 缺口 | 入口与核对重点 |
|---|---|
| 服务日志、trace、错误或延迟 | `datadog`；先确认实际 service/env 与时间窗口 |
| 白屏、客户端异常或 RN 闪退 | `sentry`；核对具体事件、版本、异常链和受影响范围 |
| 功能开关或实验差异 | 从代码识别 `growthbook` 或 `posthog-skills` 对应系统，再查环境、身份属性与实际求值 |
| Grey 服务或分支路由 | `moe-grey`；规则命中与服务发现分别核对，开关开启不能证明路由正确 |
| 业务库、缓存或事务状态 | [数据库与 Redis](database-debugging.md)；先按环境选择操作入口，再核对准确实例与对象；T2 PostgreSQL/MySQL 直接操作使用 `moe-t2-database` |
| 数仓或只读副本的数据证据 | `redshift`；区分副本/数仓的同步延迟与业务实时状态 |

具体命令和参数由对应 skill 维护；只查询能解决当前缺口的证据，不因为平台可用就全查一遍。

## 同一字段逐跳对照

用同一租户、业务对象与目标版本，比较入口、下游、mapper/converter/enricher、聚合结果和前端消费者。查清字段在何处产生、过滤、重命名、覆盖或丢失，再确定应改哪一层。

来源有数据但结果为空时，核对当前请求的身份、过滤条件、状态和时间范围。另找一条成功数据不能解释原对象的问题；应用本地的同名表也未必是权威来源。

直连 RPC 成功只证明那条调用路径；经过 BFF、Grey 或网关的请求还要保留同样的上下文核验。方法见[本地 gRPC 调试](local-grpc-debugging.md)。

## 按失败步骤展开专题

| 失败步骤 | 经验 |
|---|---|
| 注册、配置、监听或新应用部署 | [Go 服务](backend-service-handbook.md) |
| 跨请求无法关联、外部调用后缺少结果 | [业务日志](business-chain-logging.md) |
| 消息未发送、消费积压或 lag 为 0 却无结果 | [Kafka](kafka-debugging.md) |
| 查询结果、租约、缓存或数据库结构不符 | [数据库与 Redis](database-debugging.md) |
| 生成类型或安装包与运行契约不符 | 按实际产物读[legacy codegen](legacy-svc-codegen.md)、[协议包发布](api-web-publish-cheatsheet.md)或 [BFF 发布](bff-openapi-publish-cheatsheet.md) |

复验原请求及受影响行为，确保所用版本和对象仍能对应。报告已定位的失败环节、修改后的证据与未验证部分，不以另一环境的一次成功代替原问题解决。
