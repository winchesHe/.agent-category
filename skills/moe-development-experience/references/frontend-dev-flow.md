# 前端开发与页面验证经验

- ID：`MDEV-FRONTEND-DEV`
- 适用：MoeGo 前端开发中，复用已有能力、前端特有故障、请求与页面验证的方法仍有缺口时；依赖升级按下文入口读取。

## 1. 仓库指南入口

先遵循目标仓库及修改目录的 `AGENTS.md`，沿其文档入口按任务读取。技术栈、工程结构、启动与测试命令从当前仓库的 `package.json`、配置和指南确认。

- **Boarding_Desktop、moego-mobile**：按各自 `AGENTS.md` 要求，先读本仓 `docs/engineering-guides/README.md`，再加载命中的指南；两仓的指南内容并不相同。
- **其他前端仓库**：按本仓 `AGENTS.md` 指向的指南读取；没有 Agent 规则或文档索引时，再从 `README.md` 和目标模块附近的文档查找。

## 2. 找到并复用组件、query/hook 与状态能力

| 当前缺口 | 定位与复用方法 |
|---|---|
| 不知道是否已有可用组件 | 从同仓相似交互的实际 import 找到组件，核对 props、调用示例与包导出。只搜应用目录可能漏掉共享包；包来源不明时查[npm 依赖](npm-dependencies.md) |
| 已知接口，不知道从哪里接入 | 用客户端方法名或关键请求字段反查调用点，找到现有 query/hook、请求适配器及页面消费者。优先扩展这条链路，避免另建绕过现有封装的请求路径 |
| 不知道数据应放在哪里、修改后谁会更新 | 沿页面实际读取的数据追到 query、selector、atom、store 或组件内草稿，再核对写入入口与订阅者；检查同一实体的列表、详情是否读取同一份数据 |
| 共享包代码改了，消费页却没变化 | 从消费仓实际解析的包版本、链接和导出入口反查，区分已安装产物与共享仓源码；需要本地联动时读共享仓 README，不能把改了源码当成消费者已加载 |

已有封装是否可复用，要比较作用域、请求参数、返回值和更新行为；同名或外观相似不足以判定可替换。具体组件与状态 API 的选用遵循本仓指南，不把 Desktop 的实现方式套到 Mobile 或 OB。

## 3. 依赖升级入口

需要确认 package.json 升级写法、dist-tag、lockfile、消费仓升级脚本，或安装返回 404 时，读[npm 依赖](npm-dependencies.md#依赖声明与升级)及其排查章节。普通页面逻辑修改不必读取；升级后仍按下文验证真实请求、状态与交互。

## 4. 前端常见踩坑

| 现象 | 检查与处理 |
|---|---|
| 安装时报 engine / package manager 不匹配 | 对照本仓 `engines`、`packageManager` 与实际运行版本，按仓库方式选择工具链；不套用另一仓的版本或直接改约束绕过检查 |
| runtime OpenAPI 类型生成后没有目标字段的 diff | 先核对当前消费者的生成脚本、输出目录，以及它实际读取的环境/schema；再判断是否需要部署上游。细节读[legacy codegen](legacy-svc-codegen.md)，不直接手改生成文件 |
| 响应已有新值，页面仍显示旧值 | 先确认请求数据是否进入页面实际读取的缓存或状态，再检查更新/失效参数与订阅链；按本仓状态指南定位，不能只因使用 Amos 就断言 selector 有错 |
| moego-mobile 的 Metro 无法解析 workspace / link 包 | 从报错包检查 `pnpm-workspace.yaml`、实际链接和包入口，再看 `metro.config.js` 的监视与解析配置。`react-native-logger`、`react-native-traceroute` 是本仓 workspace 入口线索；先修复安装或解析问题，确认存在残留缓存后才按当前启动工具处理 |
| OnlineBooking_Go_Web 修改后页面不变 | 先确认访问的页面来自当前 dev server，并核对终端编译结果、浏览器资源与请求；请求结果正确时检查页面消费链。不能仅凭现象归因 Nuxt SSR 缓存，重启后仍需复验原操作 |

## 5. 请求、状态与交互怎样验证

以修改涉及的同一个对象和操作为线索，串起下面三处证据；不用刷新页面掩盖更新链路的问题。

| 验证位置 | 观察什么 |
|---|---|
| 请求与响应 | 用户操作是否发出预期请求，参数是否来自当前选择的对象/筛选条件，响应是否包含预期结果；已有响应字段缺失于页面时，先查前端消费路径 |
| 状态与缓存 | mutation 后，页面读取的数据是否按既有机制更新或失效；列表与详情、不同参数下的缓存是否更新到正确范围 |
| 页面交互 | 原操作后界面是否呈现结果；改动涉及切换对象、分页、重复打开或失败恢复时，验证对应场景，检查旧数据残留与失败后仍显示成功的问题 |

选择受影响模块已有的测试与检查命令；类型检查通过只证明静态类型这一层。动态页面/客户端验收按 `moe-acceptance` 执行；请求失败或环境、路由仍不明时，转到[联调与排障](debugging-and-observability.md)。

完成时说明实际验证了哪条请求、哪处更新与哪个交互结果，以及未能验证的环节；不把升级脚本成功、页面打开或测试命令退出成功当成整个修改已验收。
