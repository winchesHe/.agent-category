# 业务日志开发与排障

- ID：`MDEV-BUSINESS-LOGGING`
- 适用：MoeGo 业务日志设计与排障，尤其是请求转入异步任务后难以关联、外部调用成功却没有最终结果的场景。

## 开发时复用已有日志能力

先搜索目标应用已有日志封装与公共字段；Go 大仓可从 `backend/common/rpc/framework/log` 的调用处查起，Java/Node 等仓库按现有实现定位。沿用项目的 logger、上下文传播和字段约定，不为一个新功能引入另一套日志框架。

Go 大仓的定向搜索示例：

```bash
rg -n 'framework/log|WithContext|log\.Field' 'backend/app/<app>'
```

先选一个已有的相似业务步骤，核对日志封装、调用位置和输出字段，再确定新步骤需要补什么。包内辅助函数不是全仓公共 API，跨应用复用前检查实际归属。

## 让日志对应真实业务动作

把事件放在动作发生的位置，成功事件在操作成功返回后输出。区分“外部调用完成”“结果持久化完成”“用户读取到结果”；这几个步骤分别可能失败，不能合并成一条成功日志。

| 字段类别 | 用途 |
|---|---|
| 租户与业务对象 ID | 从用户反馈定位对应操作 |
| 异步任务或消息 ID | 跨请求、进程与重试关联 |
| 事件、结果与错误分类 | 判断停在哪一步、是否可重试 |
| 运行版本、执行范围 | 判断是否查询到了其他环境或分支 |
| 尝试轮次、耗时及单位 | 区分多次执行，定位慢步骤 |

只记录该步骤已知且有用的字段，不要求每条日志携带所有字段。异步流程不能假定保留同一个 request ID 或完整 trace；使用实际存在的任务、消息或业务关联标识，不要求所有服务都增加 `job_id`。

失败事件写清失败阶段、受控错误分类和是否安排了下一次动作；日志级别沿项目约定。区分“本次尝试失败”与“业务最终失败”，避免重试中的一次错误被解读成终态。

## 从业务对象追到失败步骤

通过 `datadog` skill 查询实际环境、服务与时间窗口，先从业务对象找到异步任务标识，再按该标识展开。字段名以当前 logger 和平台解析结果为准。

先从一条实际日志确认字段名和取值，再按业务标识、异步关联标识或具体事件缩小查询。查询语法、时间窗口、分页与聚合方法按 `datadog` skill 读取。

跨服务追踪时用实际参与服务的范围扩展查询；同一关联 ID 若没有传播到下游，回到发送与接收日志中的映射关系继续，不能仅凭时间接近认定属于同一次操作。

查异步步骤时，移除仅存在于入口日志的筛选字段；否则会把 Consumer、Dispatcher 等日志排除。业务失败事件不一定使用 Error 级别，结合事件、结果与错误码查询，不能只筛 `status:error`。

跨进程日志可能乱序到达。按业务标识、时间戳和执行轮次判断因果，不因显示顺序不同就断定流程错误。样本条数也不能代表完整数量，需要计数时用聚合能力。

## 平台没有日志时缩小范围

| 观察 | 下一步 |
|---|---|
| 源码有事件，目标 Pod 没有 | 核对镜像版本、请求是否命中该 Pod，以及是否走到该分支 |
| Pod 有事件，平台没有 | 查实际标签、属性解析、采集延迟与查询时间窗口 |
| 请求受理后缺少异步事件 | 按任务 ID 查调度、消息与消费组，见[Kafka 排查](kafka-debugging.md) |
| 外部调用完成后没有持久化成功 | 查数据库错误、事务结果与执行权，不把调用成功当作落库成功 |
| 没有外部调用事件但已有结果 | 查是否走了去重、缓存、复用或无需调用的有效业务分支 |

T2 Pod 日志使用 `moe-t2-k8s`。先按[选择 Kubernetes 入口](local-grpc-debugging.md#选择-kubernetes-入口)从当前 Host catalog 解析 `T2_KUBECTL` 并核对配置；该节同时定义依赖缺失与非 T2 的处理。Pod 未确认或已重建时，按[选择目标与端口](local-grpc-debugging.md#选择目标与端口)用真实 selector 重新查询，不沿用历史 Pod 名。

读取准确容器，重启后的失败优先看上一实例。以下为 T2 示例：

```bash
"$T2_KUBECTL" logs '<pod>' -c '<container>' --since=15m --tail=300
# 仅容器发生过重启时使用。
"$T2_KUBECTL" logs '<pod>' -c '<container>' --previous --tail=100
```

## 检查日志是否绕过正文保护

使用 ID、数量、耗时和受控错误分类完成排障。关闭业务层正文日志后，仍要检查 ORM 的慢 SQL、错误 SQL、Debug 分支和原始异常是否展开参数。

GORM 应检查实际 DB session 的 logger 配置；需要时复用项目的参数化 SQL 与 `ParamsFilter` 机制，并验证包装层确实生效。具体配置读 [GORM Logger 说明](https://gorm.io/docs/logger.html)，某个服务有保护不代表整个仓库都具备相同保护。

验证有价值的边界：成功事件不会在操作失败时输出，跨异步步骤可以用同一标识关联，正常/慢/错误 SQL 均不泄露业务正文。运行时再确认目标镜像的事件能被平台查询到。
